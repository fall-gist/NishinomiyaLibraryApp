## デザイン方針(home.html モックから抽出。以降の画面でも共通に使う)

これらはトップ画面モックで採用済みの方針。**新しい画面もこの体系を踏襲する**こと。

### カラートークン

ライト/ダーク両対応(`prefers-color-scheme` + `:root[data-theme]`)。

| トークン | ライト | 用途 |
|---|---|---|
| `--paper` | `#FAF7F1` | 画面背景(温かみのある紙色) |
| `--card` | `#FFFFFF` | カード・ヘッダー背景 |
| `--ink` / `--ink2` | `#26221B` / `#6E675C` | 本文 / 補助テキスト |
| `--line` | `#E7E1D6` | 罫線・境界 |
| `--green` 系 | `#2E6B4F` / `#E3EFE7` / `#1E4A36` | アクセント(選択・ポジティブ・受取可能) |
| `--alert` 系 | `#B3452E` / `#F7E7E2` | 期限切れ・警告・同期失敗 |

ダーク値はモックのCSS変数定義を参照。

### メンバー識別色(推奨デフォルトパレット)

spec §2 のとおり識別色は**登録時にメンバーごとに選ぶ**。モックの初期候補は以下:

| 例メンバー | 色 |
|---|---|
| パパ | `#3D6DB5` |
| ママ | `#C25278` |
| たろう | `#D98E2B` |
| はな | `#5FA05A` |
| じろう | `#8A64B8` |

識別色は**ドット+名前**の形で全画面に一貫表示する。

### レイアウト原則(トップ画面で確定した思想)

- 「返し忘れ・受取忘れを開いた瞬間に防ぐ」を最優先。**緊急度の高い順に上から**配置
- 表示データはすべて**同期結果から実際に出せるもの**に限る(モックの飾りを実装で足さない)
- 返却リストは**期限日でグループ化**。期限切れ+7日以内は全冊展開、8日以上先は折りたたみ
- 「うけとれる予約」は**取置期限でグループ化**(期限未定は末尾)。各グループ内は**1行/冊のコンパクトなリスト**で、
  **アカウント識別色**+書名(1行・省略)+利用者名。**受取館は表示しない**(2026-07-20確定・Compose実装済み)。
  ※既存の home.html モックの受取セクションはこの確定前の表示。次回モック再生成時に揃える
- **表紙画像はホームでは出さない**(決定済み)。表紙は検索結果・書誌詳細でのみ(メモリキャッシュのみ)
- 「きょうの図書館」は**既定館のみ1行**(館は設定で変更可、決定済み)
- 同期失敗時はヘッダーの最終同期時刻を赤で表示する想定
- 予約中画面の**受取可能の本は取置期限を常時表示**する(2026-07-20確定・実装済み)。
  サイト仕様上、提供可能でもEmail連絡前は取置期限が未設定のため、その場合は「取置期限 未定」と明示する

## 確定済みデザイン: ハンバーガー3画面(2026-07-20確定・同日Compose実装済み)

モックで検討し以下のとおり確定し、Composeで実装済み。

### 蔵書検索+書誌詳細([search.html](mockups/search.html))

- **2ビュー構成**: 検索画面⇄書誌詳細を同一機能内で切り替え(結果タップで詳細へ、←で戻る)
- 検索画面: 検索ボックス+**オートコンプリート候補**(公式JSON API)/ 結果リスト
  (表紙サムネ・タイトル・著者・出版社・**貸出可否○×ピル**)
- 貸出可否バッジは**タイトル行の下の独立ピル**(案A採用。サムネ角への重畳=案Bは実表紙で読めなくなるため不採用)
- **既読バッジ「よんだ」**: 読書記録とタイトルコード一致で表示(誰が・いつ+識別色ドット。複数読者の併記あり)
- 書誌詳細: 表紙(大)+書誌事項(タイトル/著者/出版社/出版年/ISBN)+既読情報+
  **所蔵一覧テーブル**(館/請求記号/配架場所/在庫状態)
- 予約は§「予約導線と予約カート」の対象メンバー選択・最終確認を経た直接予約だけを置ける。
  貸出、延長、登録変更、公式サイトカート操作のUIは置かない。表紙はopenBD都度取得・
  メモリキャッシュのみ
- **2026-07-28改定**: 予約取消をこの禁止列挙から外した。書き込み制限の撤回(`docs/spec.md`§5、
  2026-07-26)に本書が追随できていなかった更新漏れである。予約取消は§「方針: 予約取消の導線」の
  経路3のとおり、**予約中一覧から開いた場合にだけ**書誌詳細へ取消ボタンを置く

### 開館カレンダー([calendar.html](mockups/calendar.html))

- **案B採用: 3ヶ月分を縦に連ねてスクロール表示**(当月が先頭。1ヶ月+ページャの案Aは不採用)
- 一度に一館のみ。館ドロップダウン(12施設)、初期選択は**設定の既定館**
- マークするのは**休館日のみ**(凡例も「休館」のみ)。開館時刻はデータに存在しないため表示しない
- きょうの日付を強調表示。休館日データは同期時取得の約3ヶ月分(`CalendarRepository.closedDays()`)
- ※モックの休館日マークは仮表示。実装は実データを使う

### 設定([settings.html](mockups/settings.html))

セクション構成(この順):

1. **メンバー管理** — 一覧(識別色ドット+表示名+カード番号は下4桁マスク `****1234`)、
   並び替え↑↓・編集・削除、「+ メンバーを追加」。上限5人(拡張可能)
2. **メンバー追加/編集フォーム** — インライン展開。入力項目は初期登録フォーム
   (`ui/member/` の型・`MemberRegistrationForm`)と同一: 表示名/カード番号/パスワード(常に伏字)/
   識別色(プリセット5色+自由hex)。暗号化保存の注記あり
3. **同期** — 自動同期時刻(既定18:00)+最終同期日時表示
4. **通知** — 種類ごとトグル2つ(返却期限リマインダー/予約受取可能)。
   返却期限側には従属設定として**通知日数(1〜7日前、既定1日前=前日)**のセレクト(2026-07-20仕様追加)
5. **既定館** — 12施設のドロップダウン。カレンダーの初期表示と、予約カートの受取館の
   初期値に使うアプリ共通設定。既存`SettingsStore.defaultCalendarLibrary`と
   `default_calendar_library`保存キーは互換維持し、UI表記だけを「既定館」とする

実装メモ(2026-07-20実装済み): 通知日数・同期時刻・通知オンオフ・既定館は設定用DataStore(SettingsStore)に保存。
通知日数は `AppSettings.returnReminderDaysBefore`(1〜7、既定1)として追加し、`NotificationPlanner.returnReminder`
を日数可変(期限がn日後以内+超過を対象)に改修、`NotificationService` が設定値を渡す。
同期時刻の変更後は `SyncScheduleStarter.scheduleFromSettings()` でWorkManagerのスケジュールを引き直す。
メンバー編集は `RegistrationValidator.validate(form, requirePassword = false)` で
パスワード空欄=変更なしを表す(`ui/member/` の型を追加/編集の両方で再利用)。
パスワードは表示・ログ出力とも厳禁(編集時も伏字のまま)。

## 確定済みデザイン: 予約導線と予約カート(2026-07-22確定・実装済み)

### 導線

- タイトルコードを持つ既存画面、少なくとも**蔵書検索の結果・書誌詳細・新着資料の書誌詳細**から、
  対象メンバーを指定して「即時予約」または「カートへ追加」を選べるようにする。画面の余白に
  応じて両方を併置してよい
- 追加時に対象メンバーを確定し、カート画面でメンバーを暗黙に変更しない。即時予約でも同じ
  メンバー選択を要求する
- 「カートへ追加」はローカルRoomの更新だけで完結し、通信中表示を出さない。公式サイトの
  「カート」アクションには接続しない
- 「即時予約」はカートに保存せず、共通の予約バッチ処理へ一時項目1件として渡す。いずれも
  最終確認なしには予約確定を送信しない

### 予約カート画面

予約カート画面は、確定前のローカル候補と予約結果を扱う画面である。画面の表示状態は
実装済みの`ReservationUiController`を通して`ReservationCartRepository.cartItems()`、
メンバー一覧、既定館設定、12館一覧から構成する。受取館・確認待ち状態・結果は書誌詳細と共有する。
ただし処理結果・案内・エラーは起点を区別し、即時予約は対象の書誌詳細だけ、カート確定は
予約カートだけに表示する。カート結果はスクロール可能な結果ダイアログで確認する。

1. **カート項目** — メンバーごとのセクションに、識別色ドット・メンバー名・資料名・著者を
   表示する。各項目にローカルカートから削除する操作を置く。空のときは候補がない旨と蔵書検索へ
   戻る導線を表示する
2. **受取館** — 全メンバー共通のドロップダウン。`CalendarRepository.libraries`の12館を候補にし、
   設定の「既定館」を初期選択する。選択値がサイト確認画面の`receivename`候補にない場合は、
   別館へ変えずエラーを表示する
3. **連絡方法** — Email固定。`Email`の説明・選択欄・「連絡不要」選択肢は画面に出さない
4. **予約を確定** — 「対象メンバー / 資料件数 / 受取館」をまとめた最終確認
   ダイアログを表示し、肯定操作だけで`confirmCart`を呼ぶ。空カートでは無効化する
5. **結果** — バッチ完了後、メンバー別・資料別に`Success`、`AlreadyReserved`、`Failure`、
   `Unknown`を表示する。成功・重複済みの項目はカートから消え、失敗・不明の項目は残る。
   残件を再実行する場合も受取館選択と最終確認を再度要求する

即時予約も同じ確認ダイアログと結果表示を使う。失敗・不明の即時予約はカートへ自動追加しないため、
結果画面から明示的に「カートへ追加」を選べる導線を設けるかは未設計であり、実装前に決定する。

### 予約中画面との区別

- 既存の「予約中」下部タブは、サイトから同期した**確定済み予約の閲覧専用**である
- 予約カートは、確定前のローカル候補と確定結果を扱う
- **2026-07-28改定**: 従来ここには「予約中一覧の既存行を削除・変更する操作は追加しない」と
  書いていたが、予約取消のバックエンドが実サイトで検証済みになったため撤回する。予約取消の導線は
  次節のとおり予約中一覧に置く。予約カート側は従来どおり確定前の候補だけを扱い、取消は扱わない。

## 方針: 新着キーワード自動予約(2026-08-03段階13まで実装済み)

[`docs/design/new-arrival-auto-reservation.md`](design/new-arrival-auto-reservation.md)とする。

- 設定画面に初期OFFのマスタースイッチ、詳細説明、優先順のキーワードルール一覧を置く
- ルールは個別ON/OFF、ドラッグ並べ替え、含める語/除外語のタグ編集、削除確認を持つ。
  現在の新着資料とのプレビューや専用実行ボタンは置かない
- ホームに最終試行日時・概要・「最新履歴を見る」を常設する
- 完了後に初めてホームを表示した際、直近1回の詳細ダイアログを出す。別画面へは割り込まない
- 端末通知は書名・メンバー名・ルール名を含めず、「確保済みN件／見送りN件／エラーN件」だけを
  表示する。タップでホームへ移動し、通知が無効でも処理は続ける
- ホームの詳細では、今回の予約成功、既に予約済み、POST後の成否不明を別々に表示する
- 結果ダイアログと最新履歴に取消ボタンは置かず、「予約一覧を見る」から既存取消UIへ移動する。
  最新履歴では、多件数でも常に見えるよう「予約一覧を見る」をタイトル直下に固定する
- 設定の「詳細」には、日次更新・画面表示時の自動更新・新着画面の「更新」が自動予約を起こすことを
  明記する。新着画面はマスターON中であることと「更新後に予約判定する」旨を常設表示する
- 新着画面の状態表示は「新着資料を更新中」と「自動予約を判定・実行中」を分ける。専用実行ボタンや
  更新ごとの確認ダイアログは追加しない
- 手動予約・取消が自動予約の候補処理を待つ場合は「自動予約処理の完了待ち」等を表示し、
  無反応に見せない。カート予約の上部状態・確定ボタン、書誌詳細の即時予約ボタン、予約一覧の
  取消状態へ実装済み。自動予約は候補1件ごとに共通書込ゲートを解放する
- サイトが受取館を確定表示できない予約行では、アプリ記録を「アプリ送信時の指定館」として補完する。
  POST後不明由来なら「アプリ送信館（この予約への反映は未確認）」と区別し、サイト確定値を常に優先する

## 方針: 予約取消の導線(2026-07-28決定。既存3経路と自動非表示接続は実装済み)

予約取消のバックエンドは実サイトで検証済み(`docs/backend-design.md`§11.9、
`docs/handoff.md`の12回目・13回目のライブ検証)。3経路すべてが同じ`ReservationCancelRepository`を使い、
最終確認後の`cancelReservation`内部でStage 15 HARどおりの自動非表示まで処理する。実サイトでの一連成功は
2026-08-04に所有者が確認済み(`docs/handoff.md`「実サイト一連確認」参照)。

### 経路1: 予約中一覧の各行から1件取消

各行に「取消」ボタンを置き、その1件を取り消す。

### 経路2: 予約中一覧からまとめて取消

各行にチェックボックスを置き、一覧の最上部に「一斉取消」ボタンを置く。チェックされた予約を
まとめて取り消す。`ReservationCancelRepository.cancelReservations(List<ReservationCancelTarget>)`が
既に複数件・複数メンバーを受け取る契約になっており、メンバーごとに分離セッションで1件ずつ順に
処理する(1件が失敗しても他メンバーは独立して続行する)。

### 経路3: 予約中一覧から開いた書誌詳細から1件取消

予約中一覧の行をタップして開く書誌詳細に取消ボタンを置き、その1件を取り消す。

- **書誌詳細は開いた経路によって出し分ける。** 取消ボタンは予約中一覧から開いたときだけ置き、
  検索結果や新着から開いたときには置かない。
- **書誌詳細を全画面ではなくオーバーレイのポップアップで重ねる。** 予約中一覧の状態を下に保ったまま
  詳細を見て取り消せるようにする。

この2点は既存実装に前例がある。書誌詳細は既に「どの画面の上にも重ねられる共通オーバーレイ」として
実装されており(`ui/app/`)、**予約カートから開いたときだけ全画面ではなく`Dialog`で重ねる分岐が既にある**
(`current == Destination.RESERVATION_CART`)。予約中一覧についても同じ方式(`Destination`による分岐)で
実現できる見込みである。ただし現在の`BookDetailController.open(tilcod, title)`は経路情報を持たず、
分岐は呼び出し側の`Destination`で判定している。取消ボタンの出し分けをどちらで行うかは設計時に決める。

### 3経路に共通する決定事項(2026-07-28、所有者承認済み)

#### 取消済み行はアプリの一覧に出さない

**同期時に`state=CANCELLED`の予約を保存対象から除外する。** 実装箇所は
`StatusRepositoryImpl`の`database.replaceMemberSnapshot(reservations = ...)`へ渡すマッピング。

この決定が必要な理由: 取消成立時にローカルDBから即時削除するためアプリの一覧からはすぐ消えるが、
**同期は予約一覧を全置換するため、除外しないと次回同期でサイトの「取消」行が入り、
「取消済み」ラベルで再び現れてしまう**(`ReservationsScreenController.statusLabel`に該当ラベルがある)。
利用者から見れば取り消したものが復活する挙動になる。

副次的に、取消済み行を残したまま同じ書誌を再予約したときの同一`tilcod`重複も、アプリの一覧では
見えなくなる。**UI側で重複を区別する必要はない**(バックエンドは重複に対応済み)。

サイト側には取消済み行が残るため、ブラウザで見たときとの差は残る。これは許容する。
`docs/handoff.md`「今後の構想」6番(取消後に続けて非表示まで処理する)が実現すれば解消する。

なお`ReservationState.CANCELLED`と`statusLabel`の「取消済み」は削除しない。取消の成否判定と
一覧観測診断で使うため、および上記の構想で必要になるためである。

#### 選択用チェックボックスは常時表示する

各行にチェックボックスを常時置く。選択モードへの切り替え操作は設けない。行タップは経路3
(書誌詳細を開く)のままとし、**チェックボックスのタップ領域と行タップ領域を明確に分ける**こと。

#### 取消成立の2種類は利用者に区別して見せない

バックエンドは`Cancelled`(一覧に残存)と`CancelledAndHidden`(一覧から消失)を返すが、
利用者にとってはどちらも「取消が成立した」という同じ意味である。**どちらも「取り消しました」と表示する。**
内部的な区別は診断ログとドキュメントに残す。

#### 確認と結果表示

取消は不可逆なサイト書き込みであるため、**利用者の明示操作と最終確認を必ず経る**(spec §3.10の
予約確定と同じ流儀)。既存の`ReservationConfirmDialog`と予約結果ダイアログの作りを踏襲する。

確認ダイアログ:

| 経路 | 内容 |
|---|---|
| 1件取消(経路1・3) | 「予約を取り消しますか？」／資料名・メンバー名・「取り消した予約は元に戻せません。この操作の後、図書館サイトへ取消を送信します。」 |
| 一斉取消(経路2) | 「選択した◯件の予約を取り消しますか？」／メンバー別の内訳＋対象資料名の一覧(スクロール可)＋同じ注意文 |

確定ボタンは破壊的操作として警告色にし、ラベルは「取消を実行」とする(「はい/いいえ」は使わない)。

結果表示:

| バックエンドの結果 | 表示文言 | 成功扱い |
|---|---|---|
| `Cancelled` / `CancelledAndHidden` | 取り消しました | ○ |
| `Unknown`(成否不明) | **取り消せたか確認できません** ＋「予約状況を再同期して確認してください」 | × |
| `Failure` | 取り消せませんでした ＋ 理由 | × |
| `ConfirmationRequired` | 取り消せませんでした(確認画面が返りました) | × |

**成否不明を成功と混ぜないこと**が最優先である。色とアイコンも成功と分ける。一斉取消では冒頭に
「◯件取消／◯件確認できず／◯件失敗」の内訳を出す。

### 実装の段階

1. **第1段階**: 同期時の`CANCELLED`除外、経路1(行の取消ボタン)、経路2(チェックボックスと一斉取消)、
   確認・結果ダイアログ。行レイアウトを2度変えずに済むよう経路1と2は同時に作る
2. **第2段階**: 経路3(予約中一覧から開いた書誌詳細への取消ボタン、オーバーレイのポップアップ化)

## 方針: 一覧画面の行レイアウト統一(2026-08-05 所有者確定・**実装済み・確定**)

予約中一覧・貸出中一覧・読書記録で行の構成がばらついていたため、所有者の指示により揃える。
**表示だけの変更であり、通信・書き込み・成否判定のロジックには一切影響させない。**

### 1. 個別の行にメンバー名を出さない(カラードットのみ)

- 対象: 予約中一覧、貸出中一覧、読書記録。**名前のテキストを消し、カラードットだけ残す。**
- 理由: 名前は各画面上部のメンバー絞り込み行にドットとセットで出ており、行ごとの再掲は重複。
- **ドットは書誌名の左**に置く。貸出中一覧・読書記録は既にその位置。予約中一覧は現在
  ステータスラベルの右にあるので**書誌名の左へ移す**。
- 本棚は棚単位でメンバーが決まるため、**棚ヘッダのドットだけ**とし個別の本には出さない
  (現状どおり。変更不要)。
- **記録しておく副作用**: 絞り込みが「全員」のとき、行のメンバー識別はカラードットの色だけになる。
  所有者の判断で許容する。

### 2. 書誌名の太さを揃える

予約中一覧だけ`FontWeight.SemiBold`だった。**他画面と同じ既定ウェイトにする**(太くしない)。
フォントサイズは指示が無いため変更しない。

### 3. 館名に接頭辞を付けない

予約中一覧の「受取館 ○○館」を**「○○館」**にする。貸出中一覧・読書記録は既に館名のみ。
どの画面の館名が何を指すかは文脈から自明であり、通常は利用館が固定であるため重視しない。

### 4. 予約中一覧: 取置期限を予約順位と同じ位置へ

現在は「受取館/順位」行の**下に改行して**出している。**順位と同じ行・同じ位置**に置く。
取置期限(受取可能)と予約順位(順番待ち)は排他であり、両方が同時に出ることはない想定。
ただし**両方が非nullでも壊れないよう、同じRowに並べるだけの実装**にする(どちらかを捨てない)。
**受取可能時の赤太字はそのまま維持する。**

### 5. 貸出中一覧: 返却期限を書誌名の下・館名の右へ

現在は書誌名の右(行の右端)。**館名と同じ行の右側**へ移す。予約中一覧の取置期限と同じ見え方にする。

**色は赤(`alert`)をやめ、太字＋`cautionInk`(黄系)にする**(2026-08-05 所有者判断)。
「赤ほどではないが注意すべき内容」という位置づけによる。`cautionInk`は予約取消の成否不明表示で
既に使っている既存トークンであり、**新しい色は追加しない**。

- **記録しておく副作用**: 従来は延滞・返却期限間近(3日以内)のときだけ赤太字にしていたため、
  **色による延滞・期限間近の区別は無くなる**。延滞行は行の背景色(`alertBg`)と枠線で引き続き
  区別できる。区別を戻したくなった場合は延滞時だけ`alert`にすればよい。

### 6. 予約中一覧: 受取館が「未定」の行の表示

サイトの予約一覧は順番待ちの間ずっと受取館を「未定」で返す。接頭辞を消す(上記3)と
「未定　予約順位3番目」という読みにくい表示になるため、**アプリが予約送信時に記録している
受取館を使う**(所有者判断。2026-08-04の新着自動予約レビューB1で示された方針の実現)。

既に`reservation_pickup_submissions`テーブル(`memberId`・`tilcod`・`pickupLibraryCode`・`origin`)へ
アプリからの送信時に記録済みであり、館コード→館名の対応表も`CalendarRepositoryImpl.LIBRARIES`に
全12コード分ある。

表示規則:

1. サイトの受取館が実館名 → **その館名**(サイトの値を最優先する)
2. サイトが未定 かつ 記録あり・`origin = CONFIRMED_SUBMISSION` → **記録の館コードに対応する館名**
3. サイトが未定 かつ 記録あり・`origin = UNVERIFIED_SUBMISSION` → **「○○館（未確認）」**
4. サイトが未定 かつ 記録なし(ブラウザで入れた予約・記録機能より前の旧データ) → **項目自体を出さない**
5. 記録の館コードが対応表に無い(未知コード) → **項目自体を出さない**(館名を捏造しない)

**規則3を分けた理由**(2026-08-05 追記。独立レビューの指摘により是正):
`UNVERIFIED_SUBMISSION`は「予約POSTを送ったが成否が確認できなかった」記録である。
**その予約行が本当にアプリの送信で作られたという保証が無い**（利用者がブラウザで別の受取館を
指定して作った行かもしれない）。区別せずに館名だけを出すと、**不明な値を確定値として断定する**
ことになり、本プロジェクトが繰り返し踏んでいる失敗（`docs/handoff.md`進行指示15）と同型である。

本書「方針: 新着キーワード自動予約」(2026-08-03)が既に
「POST後不明由来なら『アプリ送信館（この予約への反映は未確認）』と区別し、サイト確定値を
常に優先する」と定めており、**本項目はその方針を引き継ぐ**。文言は行が狭いため
`「○○館（未確認）」`と短縮するが、**未確認であることを必ず表示に残す**こと。

**規則3で項目を消してはならない**。B1（2026-08-04の新着自動予約レビュー）の趣旨は
「万が一想定外の館で予約送信されていても、実サイトで修正できるように見せる」ことであり、
**不確実なときこそ表示する価値がある**。消すのは記録そのものが無い規則4・5だけである。

**必須の制約**: `Reservation.pickupLibrary`(サイトが返した値)を**書き換えてはならない**。
アプリの記録由来の値と混ぜると「サイトが何と言っているか」が失われ、将来サイト側の受取館が
確定したときに差分を検出できなくなる。**解決は表示組み立て(`ReservationsContentBuilder`)で行い、
Repositoryは送信記録を別の入力として提供する**こと。

## 方針: 一覧画面の行レイアウト追い込み(2026-08-05 第2次・所有者確定・**実装済み・確定**)

上記「方針: 一覧画面の行レイアウト統一」を実機で確認した所有者から、さらに3点の指示があった。

### 7. 予約中一覧のインデントを外して左詰めにする

現在は取消チェックボックスの幅(`4.dp + 48.dp`)を**全行で確保**し、取消不可の行では同じ幅の
`Spacer`を置いて行頭を揃えている。この結果、**行の内容全体が約52dp右へ寄っている**。
所有者の指示によりこれをやめ、**内容を左詰めにする**。

**チェックボックスは1行目(ステータスラベルの行)へ移す。** 単に先頭の枠を外すだけでは、
チェックボックスがMaterial3の最小タップ領域として48dpの高さを占めており、
ちょうど「ドット＋書誌名」の行と重なるため衝突する(チェックの四角は20dpで視覚的には余白に
見えるが、レイアウト上は48dp確保されている)。

変更後の行構成:

```
[☑] 順番待ち                       ← 1行目。チェックボックスは取消可能な行だけ
● 書誌名…                          ← 2行目。左端から
高須分室  予約順位3番目  [取消]     ← 3行目
```

- 取消可能な行も不可の行も、**2行目以降の行頭が揃ったうえで左詰めになる**。
- **チェックボックスのタップ領域と行タップ領域を分ける**という既存の決定(本書「選択用チェック
  ボックスは常時表示する」)は維持すること。
- 取消不可の行では1行目にチェックボックスを置かない(幅も確保しない)。

### 8. 貸出中一覧の延長ボタンを書誌名の右下へ

現在は行の外側`Row`にあり、書誌名の右(行の右端・上下中央)に置かれている。
**予約中一覧の取消ボタンと同じく、館名の行(書誌名の下)の右端**へ移す。

### 9. 貸出中一覧の返却期限を館名のすぐ右へ・文言を補う

- 現在は館名の行の**右端**に寄っている。**館名のすぐ右に少し間隔を空けて**置く
  (予約中一覧の取置期限と同じ配置。館名と期限を`Arrangement.spacedBy`で並べ、
  その組を`weight(1f)`に入れて、右端はボタンだけにする)。
- 文言の先頭に**「返却期限」**を付ける。予約中一覧の「取置期限 8/19 まで」と同じ形にする。

## 方針: 一覧画面の行レイアウト追い込み(2026-08-06 第3次・所有者確定・**実装済み・確定**)

実機確認により、3画面でメンバードットの縦位置と、書誌名より下の行のインデントが揃っていないことが
判明した。**予約中一覧の形に統一する。** 表示だけの変更であり、ロジックには影響させない。

### 現状(実機で確認された差異)

| 画面 | ドットの縦位置 | 原因(構造) |
|---|---|---|
| 貸出中 | 枠の**左上** | 外側`Row`が`Alignment.Top`。ドットはColumn(書誌名+館名行)全体の左 |
| 予約中 | **書誌名の縦中央**(2行なら行間あたり) | ドットが書誌名と同じ`Row`内・`CenterVertically` |
| 読書記録 | **枠の縦中央**(2行なら2行目の左) | 外側`Row`が`CenterVertically`。ドットはColumn全体の左 |

書誌名より下の行(館名・返却期限・予約順位・取置期限)のインデントも揃っていない。
貸出中・読書記録はドット幅ぶん下がって書誌名と揃っているが、予約中はドットが書誌名の`Row`の中に
あるため、下の行だけ左端まで出てしまっている。

### 10. ドットは書誌名と同じ行に置き、縦中央で揃える(予約中の形に統一)

3画面とも次の構造にする。

```
Column {
    Row(verticalAlignment = CenterVertically, horizontalArrangement = spacedBy(MemberDotGap)) {
        MemberDot(...)                       // 書誌名の縦中央に来る
        Text(書誌名, modifier = weight(1f))   // 2行まで
    }
    Row(modifier = Modifier.padding(start = MemberDotIndent)) {
        // 館名・返却期限・予約順位・取置期限・ボタン
    }
}
```

- **ドットに`padding(top = ...)`のような位置合わせを入れないこと。** 縦中央揃えは`Row`の
  `verticalAlignment`だけで実現する。貸出中の`Modifier.padding(top = 4.dp)`は撤去する。
- 外側の`Row`で「ドット｜Column」と横に並べる構造をやめる(貸出中・読書記録)。
  この構造だとドットがColumn**全体**の縦中央（または上端）に付いてしまい、書誌名の縦中央にならない。

### 11. 書誌名より下の行は書誌名と同じインデントにする

上記の`MemberDotIndent`(＝ドット径＋ドットと書誌名の間隔)を、書誌名より下の行の`start` paddingに
与える。**予約中一覧の館名・予約順位・取置期限の行にインデントが無い問題**はこれで解消する。

- 定数は**1か所で定義して3画面から参照**すること(`ui/components/CommonUi.kt`が適切)。
  画面ごとに数値を書かない。`MemberDot`の既定サイズ(9.dp)を変えた場合に3画面が同時に追随すること。
- 間隔は**8.dp に統一**する(予約中の現行値)。貸出中・読書記録は現在10.dpだが、
  3画面の見た目を揃えるため合わせる。したがって`MemberDotIndent = 9.dp + 8.dp = 17.dp`。
- 予約中一覧の**1行目(ステータスラベル・チェックボックス)にはインデントを付けない**。
  第2次の項目7で左詰めにしたばかりであり、対象は書誌名より**下**の行だけである。
