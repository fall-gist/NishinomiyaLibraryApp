設定画面の構成案

spec §2(アカウント)・§3.5(既定館)・§3.6(通知)・§3.7(同期)。ハンバーガーメニュー経由で開く独立画面のため下部ナビはどれも非選択。メンバー管理を最上段に置き、それ以外の設定項目を続ける構成。

1
メンバー管理は上限を明記しつつ拡張可能を示す

spec §2「5人分・拡張可能な設計」に合わせ、「4/5人・上限は拡張可能」の注記を添えた。並び替え(↑↓)は端(先頭/末尾)で該当ボタンをdisabled表示。

2
フォームはMemberRegistrationForm.ktと同一項目

表示名・カード番号・パスワード・識別色(プリセット5色+自由hex)。実装済みの初期登録フォームと入力項目・注記文言を揃え、Compose側はui/member/の型を編集フォームにも再利用する想定を示した。カード番号・パスワードは編集時も平文を画面に出さない(パスワードは伏字固定、カード番号は下4桁マスクを一覧側で徹底)。

3
同期時刻はネイティブtimeピッカー、最終同期は読み取り専用

spec §3.7「時刻は設定で変更可能」に対応。同期実行ボタンはここに置かない(手動同期はプルリフレッシュのみ、というホーム側の方針を踏襲)。

4
通知は種類ごとに2トグル

spec §3.6の表と1:1対応。「順位上昇などは通知しない」という非対応項目は増やさない。まとめて1通で届く旨をリード文で明示。

5
既定表示館は全12施設のセレクト

カレンダー画面自体は未着手だが、設定からの既定館選択のみ本画面のスコープ。カレンダー画面側の「一度に一館のみ表示」原則と対応。

判断: メンバー編集フォームの見せ方(2案、案Aを採用)

案A(採用・上のモック): リストの下にインライン展開のフォームカードとして表示例を1つ常設し、「追加」「編集」どちらでも同じ構造を使うことを示す。モック上で操作フローを省略しつつ全項目を一望できる。

案B: モーダルダイアログのオーバーレイとして重ねる案。実機の見た目には近いが、静的HTMLモックでは表示/非表示の状態を出し分けにくく、フォーム項目そのものの検討がしづらいため不採用(実装はComposeのモーダル/ボトムシートいずれでもよい)。
