# 西宮市立図書館 家族用アプリ 仕様書

最終更新: 2026-08-03(新着キーワード自動予約の段階13 待機表示を反映)

## 1. コンセプト

西宮市立図書館を使う**家族のための非公開Androidアプリ**。
家族全員分の「借りている本・返却期限・予約の状況・マイ本棚」を1つのアプリに集約し、
返し忘れ・受取忘れをなくす。

- **アプリの表示名(ランチャー名)は「西宮市立図書館」**(`app_name`)
- ストア公開はしない(家族の端末に直接インストール)
- 図書館公式サイト(LICS-XP)への書き込みは必要最小限に限る。手動の予約確定・予約取消は
  各機能の安全策のもとで実装済みである。新着キーワード自動予約は§3.11の要件が確定し、
  技術設計と設計レビューを経て、設定・実行・通知・結果表示まで実装済みである
- **2026-07-26改定**: 「自動予約や予約以外の書き込みは行わない」という制限を、リポジトリ所有者の
  判断で撤回した。撤回は「実装する」ことを意味しない。書き込み操作を追加する場合は、機能ごとに
  設計を起こし所有者の承認を得て、本仕様へ追記してから実装する。検討中のものは
  `docs/handoff.md` の「今後の構想」を参照

## 2. アカウント

- 家族**5人分**の利用者アカウントを登録できる(人数は拡張可能な設計とする)
- 各アカウント: 表示名 / 識別色 / 図書館カード番号 / パスワード
- 認証情報は**端末内に暗号化保存**(Android Keystore)。外部送信・リポジトリ格納は厳禁

## 3. 機能仕様

### 3.1 ホーム(家族統合ビュー)

- 家族**全員分を統合**したダッシュボード。メンバーは名前+識別色で区別
- 表示内容:
  - 返却期限が近い本(期限順、期限超過は強調)
  - 受取可能になった予約
  - 最終同期時刻
- メンバーによる絞り込みフィルタ

### 3.2 蔵書検索

- キーワード検索(かんたん検索相当)。オートコンプリート候補表示(公式JSON API)
- 検索結果: タイトル / 著者 / 出版社 / 貸出可否○×(公式JSON API `getIsLend`)
- 書誌詳細: 書誌事項+所蔵一覧(館 / 請求記号 / 配架場所 / 在庫状態)+予約順番待ち人数
- 書誌詳細には、同じ`tilcod`の公式サイト書誌詳細を端末の既定ブラウザで開くリンクを置く
- 検索結果・書誌詳細など、タイトルコード(`tilcod`)を持つ画面では、対象メンバーを
  指定して「即時予約」または「カートへ追加」を選べる(§3.10)。画面によっては両方を
  併置してよい

### 3.3 利用状況(メンバー別詳細)

- 貸出中一覧: 資料名 / 貸出館 / 貸出日 / 返却期限日
- 予約中一覧: 資料名 / 受取館 / 予約順位 / 予約状態 / 取置期限

### 3.4 マイ本棚(参照)

- 公式サイトの「マイ本棚」を読み取り専用で表示(資料名 / メモ / 登録日)
- 書誌詳細への導線あり

### 3.5 開館カレンダー

- **一度に一館のみ表示**(ごちゃつき防止)。表示館はドロップダウン等で選択
- 対象: 全12施設(中央 / 北口 / 鳴尾 / 北部 / 越木岩 / 若竹 / 段上 / 上ケ原 / 甲東園 / 高須 / 山口 / 義務教育校)
- 設定の「既定館」を初期表示する。既定館はカレンダー専用ではなく、予約受取館の
  初期値にも使うアプリ共通設定である(既存の保存キーとの互換性は維持する)
- 休館日をカレンダー形式で表示(公式サイトから約3ヶ月分取得)

### 3.5b 読書記録(2026-07-19追加・優先実装)

「この本、読んだことがあるか」を予約・貸出候補選びの場で即座に確認するための機能。
本アプリの中心動機のひとつ。

- データ源: 公式サイトの**読書履歴**(`gamen=usrread`)。メンバーごとに全件を取り込み、
  ローカルDBに**永続蓄積**する(他のデータと違い、同期での全削除・再取込はしない)
- 初回同期でメンバーごとに全履歴を取得(100件/ページでページング)。以降の同期は
  先頭ページから既知レコードに当たるまでの**差分取込**
- 保険として、毎回の同期時に**現在の貸出中資料も読書記録へ併合**する
  (サイト側の履歴機能が無効なメンバーでも、アプリ利用開始以降の記録は貯まる)
- 重複判定キー: メンバー+タイトルコード+貸出日
- 機能:
  - **一覧**: 貸出日の新しい順。メンバーフィルタ対応
  - **テキスト検索(必須)**: 書名・著者の部分一致。全角/半角・大文字小文字の
    ゆらぎを吸収した正規化列で検索する
  - **既読バッジ**: 蔵書検索の結果・書誌詳細に「よんだ(だれが・いつ)」を表示する
    (タイトルコード一致で判定)
- 注意: サイトの読書履歴は**アカウントごとに有効化が必要な場合がある**。
  メンバーの履歴が0件のときはその旨を表示する

### 3.6 通知

| 通知 | タイミング | 形式 |
|---|---|---|
| 返却期限リマインダー | 期限の**n日前**(既定: 前日=1日前。**日数は設定で変更可**、2026-07-20追加) | 家族**まとめて1通**(例:「明日返却: パパ3冊・長女2冊」) |
| 予約受取可能 | 同期時に受取可を検知したら | まとめて1通 |

- 順位上昇などその他の通知は**行わない**
- **通知のオン/オフ設定は必須**(種類ごとに切替可能)

### 3.7 同期

- 自動同期: **毎日18時に1回**(閉館後を想定)。**時刻は設定で変更可能**
- 手動同期: プルリフレッシュ
- 取得結果はローカルDB(Room)にキャッシュし、オフラインでも最終取得状態を表示

### 3.8 表紙画像

- openBD等の公開APIからISBNで**都度取得**
- **メモリキャッシュのみ**(アプリ終了で消える)。**ディスクキャッシュは持たない**
  (ストレージ消費を避けるため)
- 非同期・遅延ロードで、画像待ちがUI操作をブロックしないこと

### 3.9 新着資料(2026-07-20追加)

- データ源: 公式サイトの**新着資料**ページ(認証不要の公開ページ)。ジャンル一覧
  (`WOpacMsgNewMenuDispAction.do`)→各ジャンル(`WOpacMsgNewMenuToMsgNewListAction.do?newMenuCode=NN`)
- 公式サイトはジャンル別だが、本アプリは**ジャンルを保持せず全ジャンルを統合した書誌リスト**として扱う
  (tilcodで名寄せ・重複排除)
- 取得項目: 書名 / 巻次 / 著者 / 出版者 / 出版年月 / 分類 / 貸出可否(○×)/ tilcod
- ローカルDB(Room)に**全置換**でキャッシュ。画面を開いたセッションで1回取得し直し、手動「更新」も可能。
  §3.11の自動予約を有効にした場合は日次同期でも取得する
- 画面内で書名・著者の**絞り込み**ができる(読書記録と同じ正規化)
- サイト負荷配慮: 全ジャンルを巡回するため**リクエスト間500ms以上**(既存レート制御を流用)。
  自動予約が無効な場合は従来どおり画面表示時/明示更新時に取得し、有効な場合は日次同期にも組み込む

### 3.10 予約(2026-07-22確定・バックエンド実装済み)

予約機能は、ユーザーが明示操作し最終確認した予約確定だけをサイトへ送る。
直接予約通信、ローカルカート、予約カート画面・書誌詳細からの導線・最終確認画面は実装済みである。
`ReservationUiController`が受取館、最終確認、処理結果を共有する。カート追加はローカルRoom更新だけで、
図書館サイトへの予約送信は最終確認の肯定操作だけで行う。

#### 予約候補とローカルカート

- 公式サイトのカートは一切使わない。アプリ独自の**ローカルカート(Room)**だけを使い、
  カートへの追加・削除時にはサイト通信を行わない
- カートへ追加するときに、対象メンバーを必ず選択してカート項目に固定する。後から
  メンバーを暗黙に入れ替えない
- 受取館はカート追加時には固定せず、予約確定時にバッチ全体で1館を選ぶ。設定の
  「既定館」を初期選択する。メンバー別既定館は設けない
- 連絡方法は**Email固定**であり、選択UIは置かない
- 検索結果・書誌詳細などから「即時予約」も選べる。即時予約は、カートへ永続追加せず、
  共通の予約バッチ処理へ1件の一時項目として渡す

#### 確定処理と結果

- 確定前に、対象資料・対象メンバー・受取館を示す最終確認を必ず表示する。確定後は、
  項目をメンバーごとにグループ化し、各メンバーについてログイン済みの分離セッションを
  1回だけ確立して、資料を順次直接予約する。既存のリクエスト間500ms以上の制御を維持する
- POST後に成否不明となった項目ごとに予約一覧を即時1回取得し、`tilcod`を確認できた場合だけ次資料へ進む。
  即時照合済み項目は末尾再照合しない。`Submitted`/既知重複など未照合項目が残る場合だけ、処理終了時に
  予約一覧を最大1回取得して解決する。成功判定を画面alertの文言に依存させない
- 成功応答HTMLの対象資料を特定できる構造は未検証のため、確定POST後に成否不明となった項目は
  **その場で予約一覧を読み取り照合**する。対象`tilcod`を確認できた場合だけ同一セッションで次の
  資料へ進み、確認不能なら再送せず当該メンバーを停止する。この安全策により資料ごとの追加読取通信が発生する
- `Success` と `AlreadyReserved` は目的状態が達成済みなのでローカルカートから削除する。
  `Failure` と `Unknown` は残し、画面にメンバー別・資料別の部分成功結果を表示する
- 認証失敗はそのメンバーの残件だけを中止し、他メンバーは続行する。予期しないレスポンス、
  パース失敗、サイト変更の疑いでは、そのメンバーの残件を中止する
- 設定の既定館または利用者が選択した受取館が、その予約確認画面のサイト選択肢にない場合は
  エラーにする。別の館へ暗黙にフォールバックしない
- 予約送信時に指定した受取館を`memberId + tilcod`単位でローカルに記録する。サイトの予約一覧が
  受取館を確定表示できない行では、「アプリ送信時の指定館」として補完表示する。サイトが確定館を
  表示できる場合はサイト値を優先し、アプリから受取館を変更する機能は設けない
- `Success`由来の記録と、POST後不明だが送信境界を越えた記録を区別する。後者は、サイト由来の
  非取消予約行が後から確認できた場合だけ「アプリ送信館（この予約への反映は未確認）」と表示する。
  `AlreadyReserved`では今回の指定館が反映された根拠がないため記録しない

#### 再試行と書き込みの境界

- セッション切れが**確定POST前**に明確に検出できた場合だけ、新しいセッションで1回だけ
  再試行できる。確認画面の表示から確定までUI待機を挟まず、ログイン→確認GET→確定POSTを
  同一セッション内で連続実行する
- 確定POST後の通信断など、成否が不明な場合は再送しない。予約一覧の`tilcod`照合で
  `Success` / `AlreadyReserved` / `Unknown` を解決する。重複予約は`AlreadyReserved`として
  解決済み扱いにする
- 本節が定めるのは予約確定の安全策である。予約確定以外の書き込みを行わないという制限は
  2026-07-26に撤回された(§1)。新しい書き込み操作を追加する場合も、読み取り通信から分離した
  専用ゲートウェイへの隔離、副作用のある送信は一回限り、成否不明時は再送せず照合で解決、という
  本節の不変条件を同様に満たすこと

#### 設計判断

- **不採用: 公式サイトカートを正とする案。** 追加ごとに通信が必要で、アカウント切替時の
  ログイン、サイト側の残骸、部分失敗の管理が増える
- **採用: ローカルカート+直接予約。** 通信を減らし、複数アカウントを分離して扱える。一方で、
  アプリ側にカート永続化、部分成功の表示、予約一覧による照合を実装する必要がある

#### 予約取消後の自動非表示（2026-08-04実サイト一連確認済み）

- 利用者がアプリの最終確認で承認した予約取消が成立し、対象行が公式サイトの一覧に「取消」状態で
  残った場合、同じ取消処理の後続としてその行を自動で非表示にする。複数選択の一斉取消では、
  取消成立を確認できた選択行のそれぞれについて非表示まで処理する。単独の非表示ボタンや
  設定スイッチは設けない
- 過去の取消済み行、ブラウザや他端末で取り消した行、同期時に見つかった取消済み行を自動で
  非表示にしない。取消成立を確認できない場合も非表示POSTを送らない
- 非表示は取消とは別の状態変更として一回限り送信し、送信後不明では自動再送しない。完全な予約一覧で
  固定済み対象行の消失を確認した場合だけ成立とする
- 取消は成立したが非表示が失敗・成否不明の場合、取消成功は維持し、公式サイト一覧の整理だけが
  未完了または確認不能であることを結果に警告表示する。ローカル予約行は取消成立時点で削除する
- 非表示コードは取消直後の一覧から取得して処理中だけ保持し、Roomへ保存せず、再起動後や後日の同期で
  自動再開しない。詳細は`docs/design/reservation-cancel-auto-hide.md`を正本とする
- Stage 15 HARで確認した二段階POST（固定stage1 query、検証済みprevRequestFormと固定確認署名によるstage2）
  だけを使用する。2026-08-04、所有者が実機で新規予約→取消を行い、実サイトの予約一覧から対象行が
  完全に消えたことを確認した。通信レベルの詳細（method・URL・ヘッダ等)の採取は伴っていないため、
  必要な場合はライブ診断(`liveReservationHideDiagnostic`)で別途確認する

### 3.11 新着キーワード自動予約(2026-08-03段階13まで実装済み)

新着資料の書名が利用者の設定したキーワードルールに一致した場合、利用者の都度確認を待たずに
予約を試みる。マスタースイッチの初期値はOFFとし、ONの間だけ本節の自動処理を行う。

#### キーワードルール

- 当面の照合対象は**書名のみ**。巻次・著者・出版者・分類は含めないが、将来フィールドを
  拡張できる構造にする
- ルールは1個以上の「含める語」と0個以上の「除外語」からなる。正規化後の部分一致とし、
  Unicode NFKC、空白除去、小文字化により全角/半角・空白・大文字/小文字を区別しない
- 含める語はすべて一致すること(AND)。除外語は1個でも一致すれば対象外。ORはルールを分けて表現する
- 含める語同士・除外語同士は、正規化後の完全一致だけを重複として保存不可にする
- 除外語が含める語の部分文字列となる設定は無意味なため保存不可。逆に、含める語が除外語の
  部分文字列となる設定は保存できる
- ルールには個別の有効/無効と並び順を持たせる。並び順が候補資料の第一優先順位である。
  同一ルール内は出版年月の新しい順、同月は書名・巻次・`tilcod`の固定順とする
- 同じ資料が複数の有効ルールに一致しても、最上位ルールの順位を採用して試行は1回にする
- 個別ルールが無効でも、マスタースイッチがONなら照合だけを行う。他の有効ルールに一致せず、
  他の除外条件にも該当しない資料は「ルールがOFFのため予約しなかった」と結果に記録する。
  再予約防止記録は作らず、次回更新でも照合する
- 設定画面ではルールの追加・編集・削除・有効/無効・ドラッグによる並べ替えを提供する。
  含める語と除外語はタグ形式とし、ルール名の追加入力や現在の新着資料とのプレビューは設けない

#### 実行契機と候補の除外

- 新着資料の取得と全置換が正常終了した直後に実行する。日次同期、画面表示時の自動更新、
  既存の明示的な「更新」のいずれも同じ処理を通し、専用の手動実行ボタンは設けない
- 最終取得から12時間以内の鮮度抑止は画面表示時の自動更新だけに適用する。日次同期と明示的な
  「更新」は鮮度に関係なく取得する。鮮度抑止で取得を省略した場合は予約判定も行わない
- 取得結果が前回と同一でも、正常に再取得した場合は再試行可能な候補を処理する。新着取得に
  失敗した場合は予約処理へ進まない。同じ新着更新を起点とする処理が重なった場合は1回だけ実行する
- 有効ルールの一致候補、または無効ルールによる見送り候補が1件以上ある場合に限り、
  予約POSTまたは見送り確定の前に各メンバーの最新の予約・貸出状況を取得する。
  読書記録はローカルの永続データを用いる
- 家族の誰かが同じ`tilcod`を予約中・貸出中、または読書記録に保持している資料、および過去に
  自動予約成功・予約済みと確定した資料、成否不明・拒否等で再送禁止の終端制御記録がある資料は
  除外する。同じ作品でも`tilcod`が異なる別版は別資料として扱う
- 予約一覧に取消済み行しかない資料は「予約中」とみなさない。同一`tilcod`に取消済み行と
  非取消行が併存する場合は、非取消行が1件以上あれば予約中として除外する
- 予約一覧の完全性を確認できないメンバーも予約先候補には残す。見つかった非取消行は除外根拠に
  使うが、対象が見つからないことは家族内の不在証明には使わない。同一メンバーの重複は
  サイトの`AlreadyReserved`で終端にし、POST後の成否照合では改めて一覧完全性を要求する
- 除外・試行結果を制御用記録として、最初に候補または除外となった日から暦上の2か月間保持する。
  再試行しても期限を延長しない。表示用の実行履歴とは分離する

#### メンバー割当と予約結果

- キーワードルールにメンバーを固定しない。設定画面のメンバー並び順を優先順位とし、資料ごとに
  最上位メンバーから予約を試みる。家族内で同じ資料を成功扱いにするのは最大1人とする
- 予約成功・予約済みならその資料を終了する。明示的な予約上限超過、またはPOST前と確定できる
  認証・通信失敗なら次順位メンバーを試す
- 上限は資料区分ごとに異なる可能性があるため、ある資料で上限超過したメンバーも、次の資料では
  再び最上位から試す。全メンバーが上限超過、またはPOST前失敗なら次回新着更新で再試行する
- 上限以外の明確なサイト拒否では次順位へ送らず、自動再試行しない。POST後の成否不明でも、
  実際には成立している可能性があるため次順位へ送らず、2か月の保持期間中は自動再試行しない
- アプリ独自の予約冊数上限は設けない。設定内容と入荷状況によって予約枠が一度に埋まる可能性を
  機能説明に明記し、不要な予約は予約一覧から利用者が手動で取り消す
- 受取館は処理開始時点の設定の既定館を全候補に使用し、連絡方法はEmail固定とする。既定館未設定、
  またはサイトの選択肢にない場合はPOSTせず、設定修正後の次回更新で再試行する
- 処理開始時点のマスタースイッチ、ルール内容・順序、メンバーID・表示名・順序、既定館を
  その回のスナップショットとして固定する。実行中に追加されたメンバーは次回から対象とし、
  削除されたメンバーは各POST直前の現存確認以降の処理を止める
- 予約確定POSTは既存の専用ゲートウェイ、安全な一回限りの送信、予約一覧による成否照合を再利用する。
  POST後の成否不明を自動再送してはならない
- 手動予約・即時予約・自動予約・予約取消はアプリ共通の書込ゲートで直列化する。自動予約は
  候補1件単位でゲートを解放し、手動操作を全候補完了まで待たせない。間に別の書込が入った場合は、
  次候補の前に最新利用状況を取得し直す

#### 設定・結果表示・通知

- 設定画面に「新着資料の自動予約」マスタースイッチを置き、初期値をOFFとする。ONにする時点では
  有効ルール1件以上、メンバー1人以上、既定受取館を必須とする。通知権限は必須にしない
- ONの後に設定不足となってもスイッチを暗黙にOFFへ変えない。有効ルールが0件なら照合せず設定画面に
  表示する。有効ルールの一致後にメンバーまたは既定館不足が判明した場合はPOSTせず結果へ記録する
- キーワード設定の近くに「詳細」ボタンを置く。確認なしで予約すること、メンバー優先順、
  予約枠が一度に埋まる可能性、手動取消とキーワード見直し、端末通知OFFでも処理を続けること、
  日次更新・画面の自動更新・新着画面の「更新」が自動予約を起こすことを説明する
- ルール追加・編集・並べ替え・有効化だけでは実行せず、次回新着更新から判定開始時点の設定を適用する。
  すぐ判定させたい場合も既存の新着資料「更新」を使う
- 表示用履歴は、報告対象がある直近1回分だけを保持する。成功・上限超過・認証/通信エラー・
  成否不明・設定不足・個別ルールOFFによる見送りを、書名、一致ルール、試したメンバー順、
  割当メンバーとともに表示する。正常な除外や一致なしでは履歴を上書きしない
- 予約処理を行った場合はAndroidの端末通知を1件出し、書名・メンバー名・ルール名を含めず、
  「確保済みN件／見送りN件／エラーN件」の件数だけを表示する。`Success`と`AlreadyReserved`は
  確保済み、全メンバー上限超過・設定不足・個別ルールOFFは見送り、認証・通信・パース・
  メンテナンス・サイト拒否・POST後不明はエラーとする。正常除外は件数に含めず、OFFルールだけの
  見送りなら通知しない。端末通知が無効でも処理は継続する
- 通知タップ時はホームを開く。完了後に初めてホームを表示した際、またはホーム表示中に完了した際は、
  詳細ダイアログを1回表示する。別画面へは割り込まない。未確認のまま次の結果が出た場合は最新分で置き換える
- ホームの詳細では`Success`、`AlreadyReserved`、POST後不明を独立表示する。新着画面はマスターON時に
  更新後に予約判定を行うことを常設表示し、「新着資料を更新中」と「自動予約を判定・実行中」を区別する
- ホームには最終試行日時・概要と「最新履歴を見る」を常設する。ダイアログには「閉じる」
  「予約一覧を見る」「最新履歴を見る」を置く。取消操作は結果・履歴には置かず、予約一覧へ集約する
- 手動カート予約・即時予約・予約取消が自動予約の共通書込ゲート解放を待つ間は、各操作画面に
  「自動予約処理の完了待ち…」を表示する。手動操作同士の待機ではこの専用文言を表示しない

### 3.12 貸出延長(2026-08-04設計確定・2026-08-05実装完了・実サイト確認済み)

貸出中一覧のうち、サイトが延長可能と示している資料について、利用者が明示操作で返却期限を
延長できるようにする。技術設計は`docs/design/loan-extension.md`を正本とする。

技術設計§11の全7段階を2026-08-05に完了し、所有者が実機(CIのAPK)でアプリの通常操作による
延長の実サイト成立を確認済みである(`docs/handoff.md`「段階7 実サイト一連確認」参照)。
下記の要件はいずれも実装済みだが、**拒否時のサイト応答構造は今回も実測できておらず**、
最後の項目(拒否理由を区別しない)は現在も有効な制約である。

- 貸出中一覧の各行のうち、サイトが延長ボタンを提示している資料にだけ延長操作を表示する
- タップ後、アプリ独自の確認（資料名・現在の返却期限）を経てから送信する。サイトの確認ダイアログの
  文言は転記しない
- 延長は既存の予約確定・予約取消と同じ専用ゲートウェイへ隔離し、送信は一回限りとする。POST後の
  成否不明は自動再送しない
- 成否は返却期限日の変化で判定する。サイトの成功・失敗メッセージは得られないため、メッセージ文言に
  成否判定を依存させない
- 一斉延長・複数選択・書誌詳細からの延長導線は当面設けない。ただし通信部分（Gateway/Repository）は
  呼出し元の画面に依存しない構造とし、後から導線を追加できる状態を保つ
- 延長可否の表示にはRoomへ保存する可否フラグを使い、実際の送信に使うコードは実行時に取得し直す。
  古いコードで送信しない構造とする
- 拒否時のサイト応答は未実測のため、初期実装では拒否理由を区別せず成否不明として扱う。
  拒否例を実測できた時点で分類を追加する
- 貸出延長は予約データに触れないため、予約系の共通書込ゲートには参加させない

### 3.13 マイ本棚の編集(2026-08-08要件確定・設計未着手)

§3.4の参照専用だったマイ本棚を、アプリから編集できるようにする。サイト側の通信は
`docs/site-research.md`§13で採取済みである。

対象とする操作は次の6つ(2026-08-08所有者決定)。

- 資料を本棚へ追加する(メモを同時に入力できる)
- 本棚から資料を削除する
- 登録済み資料のメモを編集する
- 本棚を新規作成する
- 本棚の名前を変更する
- 本棚を削除する

要件:

- **追加の導線は書誌詳細に置き、メンバーと追加先の本棚を毎回選ばせる。** 予約カートの受取館選択と
  同じ形とする。設定に既定本棚を持つ方式は採らない(2026-08-08所有者決定)
- 資料の削除・メモ編集・本棚の管理は本棚画面を起点にする
- **本棚の削除は中の資料もまとめて消える不可逆操作であるため、他の操作より重い確認を置く。**
  対象の本棚名と、消える資料の件数が分かる確認とする
- 書き込みは既存の予約確定・予約取消・貸出延長と同じく専用ゲートウェイへ隔離し、利用者の明示操作と
  確認を経た場合だけ送信する。送信は一回限りとし、POST後に成否不明なら再送しない
- **成否はサイトの成功メッセージの文言ではなく、本棚の内容を取得し直して照合することで判定する**
- サイトの編集画面は本棚単位の一括フォームであり、資料ごとの部分送信ができない。1件のメモを
  変えるだけでも本棚内の全資料を順序どおり送る必要がある。この制約をアプリの操作単位の設計に反映する
- 同じ資料を同じ本棚へ二重に追加することはサイトが拒否する。アプリはこれをエラーとして扱わず、
  既に登録済みである旨を利用者へ伝える

## 4. 非機能要件

- **サイト負荷への配慮**: 自動同期は1日1回。リクエスト間の最小間隔500ms(`LicsXpSession`)は維持する。
  > 2026-07-28改定: 手動更新の5分クールダウンは所有者の判断で撤回した。家庭内のみでの使用を
  > 想定しており、サーバに負荷となるほどのリクエストを送ることはそもそもできないため、利用者の
  > 良心に委ねる。5分間隔では実機検証にも支障があった。リクエスト間の最小間隔500msは今回の対象外で、
  > 引き続き維持する。
- **パーサの分離**: スクレイピング部分は独立モジュールとし、サイト改修時に
  差し替えやすくする。パース失敗はアプリ内で検知・表示する
- **予約の安全性**: 手動予約は明示操作と最終確認を通った場合だけ送信する。§3.11の自動予約は
  利用者がマスタースイッチとルールで事前許可した範囲だけ送信する。いずれも成功は予約一覧の
  `tilcod`照合で検証し、POST後に成否不明なら再送しない
- **拡張性**: 予約直接実行は既存の読み取り通信から分離した境界に置く。予約確定以外の書き込みを
  追加する場合も同じ境界の内側に置き、機能ごとに本仕様へ追記してから実装する
- 対応OS: Android 8.0 (API 26) 以上

> 予約確定以外のサイト書き込み操作」を本節から削除した。所有者の判断で制限を撤回したことによる(§1)。
> 削除は実装を約束するものではなく、個別の設計と承認を経て初めて実装対象になる。

- ISBNバーコードスキャン(不要と判断)
- 予約順位の上昇通知
- 表紙画像のディスクキャッシュ
- ストア公開・多言語対応
