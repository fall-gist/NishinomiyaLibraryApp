# 待ち時間の表示を画面下の帯へ移す 設計書

作成日: 2026-09-26
状態: **設計中（§7 の2点を所有者へ確認中）**
報告: 所有者（2026-09-20）「複数書誌の本棚追加は、進捗をダイアログで表示して終わるまで移動できない。
ダイアログではなく画面上のどこかに小さいメッセージとして表示し、その間も移動できるようにしたい
（ただし本棚追加はできない）。本棚追加だけでなく、他の待ち時間が発生する操作全般で同様にしてほしい。
メッセージは画面最上部か最下部にオーバーレイで出して画面遷移後も残る形がわかりやすいか」

所有者の確定事項（2026-09-20、モックへの回答）: **帯は画面の下に出す。**

## 1. 現状（確認済み）

待ち時間が発生する操作と、いまの待ち時間の見せ方は次のとおり。

| 操作 | 状態の持ち主 | いまの表示 | 処理中に画面を移れるか |
|---|---|---|---|
| 一斉本棚追加 | `BookshelfEditingUiController.bulkAddProgress` | **閉じられないダイアログ**（`BookshelfScreen.kt:389`、件数付き） | **移れない** |
| 単件の本棚編集（作成・削除・資料の追加・削除・編集） | 同 `processingMutation` | ボタンの無効化のみ | 移れる |
| 一斉延長 | `LoanExtensionUiController.bulkProgress` | 貸出中画面の中に「延長処理中… N件目/M件」（`LoansScreen.kt:141`） | 移れる（表示は見えなくなる） |
| 単独延長 | 同 `processingTarget` | 行の中に「延長処理中…」 | 移れる |
| 一斉取消 | `ReservationCancelUiController.processing` | ボタンの無効化のみ（件数の進捗は無い） | 移れる |
| 一斉カート追加 | 各画面の `bulkCartAdditionProcessing` | ボタンの無効化のみ | 移れる |
| 一斉直接予約 | 各画面の `bulkDirectReservationProcessing` | ボタンの無効化のみ | 移れる |
| カート確定（予約の実行） | `ReservationUiController.processing` | ボタンの無効化のみ | 移れる |
| 手動同期 | `SyncUiController.isSyncing` | プルリフレッシュのインジケータ、ホームの「同期中…」、完了時に Snackbar | 移れる |

**「処理中に同種の操作を禁止する」仕組みは既にある**（各画面の `enabled` 条件、`bookshelfEditingProcessing`、
`ReservationOperationGate` と `BookshelfStateGate` による排他）。今回これを変える必要はない。

したがって今回の実体は次の2つである。

1. 一斉本棚追加の**閉じられないダイアログをやめる**（これだけが画面を移れない原因）
2. 待ち時間の表示を、画面ごとの表示から**画面下の共通の帯へ移す**（画面を移っても見えるようにする）

## 2. 設計

### 2.1 帯の置き場所

`LibraryApp` の `Scaffold` の中で、**下部ナビゲーションの直上**に出す。

- `Scaffold` の `bottomBar` に、ナビゲーションバーと帯を縦に積む（帯が下、ナビが最下段ではなく、
  **帯がナビの上**）
- Snackbar（手動同期の結果）とは重ならない位置にする。Snackbar はさらに上に出る
- 書誌詳細・診断ログのオーバーレイより**下**に置く（全画面オーバーレイの上に帯を重ねない）。
  詳細を見ている間は帯が隠れるが、処理は続いており、閉じれば再び見える
- 進行中の操作が無いときは**何も描かない**（高さ0）

### 2.2 帯の中身を純関数で決める

このプロジェクトには、表示文言を Android 非依存の純関数へ置いてテストで固定する前例が多い
（`LoansContentBuilder.dueLabel`、`ReturnReminderTextBuilder.title` ほか）。今回もそれに倣う。

```kotlin
/** 画面下の帯に出す進行中の操作。null なら帯を描かない。 */
data class OperationProgressBanner(val text: String)

object OperationProgressContentBuilder {
    /**
     * 進行中の操作から帯の文言を決める。複数が同時に進むことがあるため、
     * **優先順位をつけて1つだけ出す**（§2.4）。
     */
    fun banner(
        bookshelfBulkAdd: BookshelfBulkAddProgress?,
        loanBulkExtend: LoanExtensionBulkProgress?,
        cancelProcessing: Boolean,
        cartAddProcessing: Boolean,
        directReservationProcessing: Boolean,
        cartConfirmProcessing: Boolean,
        bookshelfMutationProcessing: Boolean,
    ): OperationProgressBanner?
}
```

**新しいコントローラは作らない。** `LibraryApp` は既に全コントローラを受け取っており、
各 state を購読して上記の純関数へ渡すだけで足りる。状態を二重に持つと、更新の取りこぼし
（過去に繰り返し踏んだ lost update）の温床になる。

### 2.3 文言

件数の進捗があるものは件数を出す。無いものは操作名だけを出す。

| 操作 | 帯の文言 |
|---|---|
| 一斉本棚追加 | `本棚へ追加しています　N件目/M件` |
| 一斉延長 | `延長しています　N件目/M件` |
| 一斉取消 | `予約を取り消しています` |
| 一斉カート追加 | `カートへ追加しています` |
| 一斉直接予約 | `予約しています` |
| カート確定 | `予約しています` |
| 単件の本棚編集 | `本棚を変更しています` |

件数の数え方は既存の表示に合わせる（`minOf(completed + 1, total)`。`docs/design/bulk-bookshelf-add.md`
で「6件目/5件」と出た不具合を直した際の規則）。

### 2.4 同時に複数が進んでいるとき

排他の仕組みがあるため、同じ資料に対する操作が同時に進むことは無い。しかし別系統の操作
（例: 本棚追加の最中に手動同期）は同時に起こりうる。**帯は1本だけ出し、優先順位で1つ選ぶ。**

優先順位は「サイトに書き込む操作 > 読み取りだけの操作」とし、書き込みの中は上表の順とする。
2本以上並べると帯が画面を占め、下部ナビを押しにくくなる。

### 2.5 一斉本棚追加のダイアログを廃止する

- `BookshelfScreen.kt` の `BookshelfBulkAddProgressDialog` を削除する
- 結果のダイアログ（`BookshelfBulkAddResultsDialog`）は**残す**。`LibraryApp` から
  `BookshelfEditingDialogs` を呼んでいるため、どの画面にいても結果が出る（確認済み）
- 処理中に同じ操作をさせない仕組みは既にある（`bookshelfEditingProcessing` を各画面が見ている）。
  ダイアログを消しても、この禁止は効いたままである

### 2.6 画面の中の待ち時間表示をどうするか

- 貸出中の「延長処理中… N件目/M件」（一斉延長の進捗）は**帯へ移す**（画面からは消す）
- 行の中の「延長処理中…」（単独延長。どの行を処理しているかを示す）は**残す**。
  行ごとの情報であり、帯では表せない
- ボタンの無効化は現状のまま

### 2.7 スコープ外

- **手動同期は帯に出さない**（§7-2 で所有者に確認する）。プルリフレッシュのインジケータと
  ホームの「同期中…」、完了時の Snackbar が既にあり、三重になる
- **完了の知らせは帯に出さない**（§7-1 で所有者に確認する）。結果は既存の場所に出す。
  帯は進行中だけを示し、終わったら消える
- 排他の仕組み（ゲート）、確認ダイアログ、結果表示の中身は変えない
- 新着資料の巡回（自動・手動）の進捗表示（`updatePhase`）は変えない

| ファイル | 変更 |

## 4. テスト計画（決定論的）

`OperationProgressContentBuilder.banner`（純関数）:

1. 何も進行していなければ null
2. 一斉本棚追加の進捗があれば「本棚へ追加しています　3件目/5件」
3. 件数が総数を超えないこと（`completed + 1 > total` のとき「5件目/5件」）
4. 一斉延長の進捗があれば「延長しています　2件目/4件」
5. 一斉取消・一斉カート追加・一斉直接予約・カート確定・単件の本棚編集で、それぞれの文言になる
6. 複数が同時に真のとき、優先順位の高い1つだけが選ばれる（組み合わせを数通り固定する）

UIの見た目（帯の位置、下部ナビとの重なり）は自動テストで固定しない。実機確認で担保する。

## 5. 手動確認（CIのAPKで実機）

1. 蔵書検索から一斉本棚追加を実行 → **ダイアログが出ず**、画面下に帯が出る
2. その間に他画面へ移れる。帯は移った先でも出ている
3. その間、本棚への追加は実行できない（ボタンが押せない）
4. 完了すると帯が消え、結果のダイアログが出る（どの画面にいても出る）
5. 一斉延長・一斉取消・一斉カート追加・一斉直接予約・カート確定で、それぞれ帯が出る
6. 帯が出ている間、下部ナビのタップが妨げられない
7. 書誌詳細を開くと帯は隠れる。閉じると再び見える
8. 手動同期の完了メッセージ（Snackbar）と帯が重ならない

## 6. 未解決・既知のリスク

1. 処理中に画面を移れるようになると、結果表示を見ないまま別の操作を始める余地が広がる。
   排他の仕組みは効いているため、取り返しのつかない二重送信は起きない
2. 帯は1本だけ出すため、同時に進む2つ目の操作は見えない（§2.4）

## 7. 所有者へ確認したいこと

1. **完了を帯で知らせるか。** いまの案は「進行中だけ帯に出し、終わったら消す」。結果は既存の
   ダイアログやメッセージで見る形である。「○件を追加しました」を数秒だけ帯に出す案もある
2. **手動同期を帯に出すか。** いまの案は出さない（既に3か所で分かるため）
