# マイ本棚編集: 実サイト通信の採取手順書

状態: 所有者による採取待ち（2026-08-08作成）
対象機能: マイ本棚の編集（資料の追加・削除・メモ編集、本棚自体の作成・名前変更・削除）

**この文書は所有者がブラウザで操作しながら読むためのものである。** 採取が終わるまで、
アプリ側の実装には着手しない（`docs/handoff.md`進行指示10）。

## 1. なぜ採取が先か

本棚編集はすべてサイトへの書き込みである。予約確定・予約取消・貸出延長では、実測前に
プロトコルを推測して実装し、いずれも「全テストが通るのに実サイトでは動かない」状態を作った
（進行指示13・14、貸出延長では同じ失敗の3度目）。同じ轍を踏まないため、**method・URL・
全フォーム項目・確認段階の有無を実測してからでなければ送信部分を書かない。**

現時点で分かっているのは、ページ内JavaScriptから読み取れる**入口のアクション名だけ**である
（未ログイン状態のフィクスチャ由来。値も遷移先の画面構造も未取得）。

| 操作 | 入口のアクション | 分かっていること |
|---|---|---|
| 資料を本棚へ追加 | `WOpacTifDetailAddBookListAction.do` | 書誌詳細に`select name=booklist`とメモ欄`commnt`、`btnflg=1`がある |
| 本棚の管理画面へ | `WOpacSdiBookListToSdiMainteAction.do` | 遷移先は`tiles.WSdiBookListMainte`。**中身は未取得** |
| 本棚の新規作成へ | `WOpacSdiBookListToInputAction.do` | 遷移先は`tiles.WSdiBookListNew`または`tiles.WSdiInput`。**未取得** |
| 本棚まるごと削除 | `WOpacSdiBookListDelAction.do?delflg=1` | クエリ`delflg=1`付き。確認段階の有無は**未確認** |
| 本棚の切り替え | `WOpacSdiBookListToOtherBookDispAction.do?flg=1` | 実装済み（表示切替のみ） |

**資料単位の削除・メモ編集がどのアクションなのかは、まだ全く分かっていない**（管理画面の中に
あると推定しているだけ）。S1でその画面を採ることが今回の要になる。

## 2. 採取前の準備

1. PCのChromeで公式サイトへ**ログインまで済ませておく**。
   **ログイン操作はHARに含めない**（カード番号・パスワードが記録されるため）
2. DevToolsを開き、Networkタブで **Preserve log を ON** にする
3. `window.confirm`や`window.alert`を**書き換えないこと**。ページ遷移で消えるうえ、
   サイトの重要な分岐を潰す（進行指示12）
4. 保存は右クリック →「Save all as HAR with content」。**操作ごとに別ファイル**にし、
   ファイル名に手順番号を入れる（例: `S3-create-shelf.har`）

### 秘匿の扱い

HARには`JSESSIONID`・`hash`・利用者情報が含まれる。

- **HARをリポジトリへコミットしないこと。** 受け渡しは作業用の一時フォルダで行う
- フィクスチャ化するときはこちらで値をマスクする
- 既存の`app/src/test/resources/fixtures/mybooklist.html`には`hash`の実値が残っている
  （2916行目）。既に失効した値だが、本件のfixture追加時に方針を揃えて処理する

## 3. 採取の順序（この順で行う）

**既存の本棚には一切触らない。** テスト用の本棚を1つ作り、その中だけで削除まで行って、
最後にその本棚ごと捨てる。これにより不可逆な操作を実データへ当てずに全操作を採取できる。

各手順で記録してほしいもの:

- HARファイル
- **確認ダイアログが出たか。出たなら文言をそのまま（スクリーンショットで可）**
  ← 予約取消・貸出延長と同じ二段階POSTかどうかの判定に必須
- 操作後の画面で何がどう変わったか（成功メッセージの有無、一覧からの消失など）

| # | 操作 | 書込 | 目的 |
|---|---|---|---|
| S0 | マイ本棚を開く（既存の本棚のまま） | なし | 一覧の初期状態と`hash`の出方を記録 |
| S1 | 「リストの管理」ボタンを押して管理画面を開く | なし | **最重要。** 資料の削除・メモ編集のコントロールがここにあるかを確認する |
| S2 | 管理画面から戻る／「本棚の新規作成」画面を開く | なし | 作成フォームの項目を確認 |
| S3 | テスト用の本棚を作成（名前は「テスト棚」等、捨ててよいもの） | あり | 本棚作成の通信 |
| S4 | 書誌詳細を開き、テスト棚へ資料を追加（**メモも入力する**） | あり | 追加の通信。メモありの形 |
| S5 | もう1冊、**メモを空のまま**追加 | あり | メモ未入力時の送信値の違いを見る |
| S6 | 管理画面で、S4で入れた資料のメモを書き換えて保存 | あり | メモ編集の通信 |
| S7 | 管理画面で、S5で入れた資料を削除 | あり | 資料削除の通信 |
| S8 | テスト棚の名前を変更 | あり | 名前変更の通信 |
| S9 | 「このリストの削除」でテスト棚ごと削除 | あり | 本棚削除の通信。**不可逆。対象がテスト棚であることを必ず確認してから押す** |

S4・S5で使う資料は何でもよい（予約も貸出も発生しない）。

### 特に見てほしいこと

- **S1**: 資料ごとにチェックボックスがあるか、削除ボタンが行ごとか一括か、メモが
  テキスト入力欄になっているか。この画面の構造がフェーズ全体の設計を決める
- **S6/S7**: 保存・削除を押したあと、確認画面をもう一枚挟むか（＝二段階POSTか）
- **S9**: 中の資料ごと消えるのか、確認が何段あるか

## 4. 採取後にこちらが行うこと

1. HARから各操作のmethod・完全URL・フォーム項目（DOM順・同名重複を含む）・確認段階を確定し、
   `docs/site-research.md`へ観測事実として記録する
2. 機能要件を`docs/spec.md`へ追記し、所有者の承認を得る（禁止事項1）
3. 技術設計を`docs/design/`へ起こす。書き込みは専用ゲートウェイへ隔離し、送信一回限り、
   POST後不明は再送せず照合で解決、という既存の不変条件を踏襲する
4. 実装・レビュー・実機確認

## 5. 決定済みの要件

- **追加時はメンバーと本棚を毎回選ぶ**（2026-08-08所有者決定）。予約カートの受取館選択と同じ形。
  設定に既定本棚を持つ案は採らない
- 対象操作は資料の追加・削除・メモ編集、本棚自体の作成・名前変更・削除の全部（同日決定）
- 採取は先に一括で行い、以降は所有者の手を煩わせずに設計・実装を進める（同日決定）

## 6. 未決（採取結果を見てから決める）

- 資料削除・メモ編集が一括操作しかできない画面だった場合のUIの持たせ方
- 本棚まるごと削除をアプリのどこに置くか（不可逆かつ中の資料も消えるため、確認の重さを設計する）
- 追加成功後にローカルDBへ即反映するか、次の同期を待つか（予約取消は即時削除の前例あり）
