# 新規アカウント対応と本棚操作の対象ズレ修正

状態: 設計確定（2026-08-16作成・同日承認）。実装未着手。
対象: 所有者が実機で遭遇した3件の不具合をまとめて修正する。

## 0. 症状と原因の対応

| # | 症状 | 原因 | 確度 |
|---|---|---|---|
| 1 | 本棚削除で**対象と異なる本棚が消える**（末尾以外を指定したとき） | サイトは `otherbook` を見ず、**セッション上のカレント本棚**を削除する。アプリはスナップショット取得の巡回でカレントが末尾になったまま送信している | **確定** |
| 2 | 新規アカウント（本棚0件）で同期・本棚作成が失敗する | 本棚0件だと `mybooklist` が新規作成画面を返し、`ShelfListParser` が `ParseException` を投げて**同期全体が落ちる** | **確定** |

## 1. 本棚のカレント同期（症状1）

### 1.1 実測で分かったこと

2026-08-15採取のHAR（`tosho.nishi.or.jp.har`、本棚1・2・3のうち**2を削除**）:

- 削除前の `select[name=otherbook]` は `1` / `2` / `3` で、**`2` が SELECTED**
- 1段階目: `POST WOpacSdiBookListDelAction.do?delflg=1`
  body = `hash`, `returnid`, `gamenid=tiles.WSdiBookList`, `tilcod`, `btnflg`, `otherbook=2`
  **Referer = `WOpacSdiBookListToOtherBookDispAction.do?flg=1`**
- 2段階目: `POST WOpacSdiBookListDelAction.do`（クエリなし）
  body = 上記 + `delflg=1` + `okCodes=OPACSDI010`
- 3段階目: `POST WOpacSdiBookMyListDispAction.do`
  body = 上記 + `jp.co.necsoft.licsxp.base.util.validation.MessageUtil.CONFIRM_DIALOG_SEND_REDIRECT=true`
- 削除後の `select[name=otherbook]` は **`1` と `3`**（2が消えた）

**Referer が示すとおり、ブラウザは削除の直前に対象本棚へ切り替え、それを表示した状態から削除している。**

### 1.2 なぜ「カレントが対象」と言えるか

HAR単体では、サイトが `otherbook` を見ているのかカレント状態を見ているのかを**分離できない**
（今回はどちらも `2` で一致しているため）。しかし次の2つを合わせると確定する。

- HAR: カレント=2、`otherbook=2` → **2が消えた**
- アプリの実機観測: カレント=末尾、`otherbook=対象`（末尾以外）→ **末尾が消えた**

`otherbook` の値が対象を決めているなら、アプリでも対象が消えるはずである。消えていない以上、
**決定要因はカレント状態**である。

### 1.3 アプリ側の作り込み

スナップショット取得（[BookshelfGateway.kt:359-368]）は全本棚を順に切り替えて巡回するため、
**ループを抜けた時点でカレントは一覧の末尾**になる。変更操作はそのとき保存した
**キャッシュHTML** からフォームを組み立てて送るため、カレントは末尾のまま動かない。

これで所有者の観測3つがすべて説明できる。

| 観測 | 説明 |
|---|---|
| 末尾以外を指定 → 末尾が消える | カレントが末尾のまま |
| 末尾を指定 → 成功 | たまたまカレントと一致 |
| 本棚1つだけ → 削除はできるがエラー | カレント＝唯一の棚。エラーは削除後に0件となり新規作成画面が返るため（症状2） |

### 1.4 修正

**本棚単位で対象を指定する変更操作の直前に、対象本棚へ切り替える。**

対象操作: 本棚削除・本棚名変更・資料メモ更新・資料削除。

手順:

1. `WOpacSdiBookListToOtherBookDispAction.do?flg=1` を `otherbook=対象` で送る
   （スナップショット取得で既に使っている実測済みの通信。新規プロトコルではない）
2. 応答を `ShelfParser` で解析し、**`shelf.no` が対象と一致することを確認する。
   一致しなければ状態変更POSTを送らずに停止する**（フェイルクローズ）
3. **切り替え応答のHTMLからフォームを組み立てる。** キャッシュHTMLを使わない。
   トークン（`hash`）も切り替え応答のもので更新する
4. 以降は既存の2段階POSTと成否裁定をそのまま使う

**資料追加（AddItem）は対象外とする。** 書誌詳細から `booklist=対象本棚番号` を送る別経路であり、
カレント依存かどうかは**未検証**である。現に所有者からの誤登録報告もない。
必要性を単独検証していない変更は行わない（`docs/handoff.md` 進行指示7）。
**ただし同じ危険がある可能性は残るため、リスクとして§5に記録する。**

3段階目（`WOpacSdiBookMyListDispAction.do` の表示遷移）は**送らない**。
現行実装は `UPDATE` 系でのみ完了ダイアログ用の遷移POSTを送っており、削除は2段階で成立している
（所有者の観測「末尾の本棚は正常に削除できる」が根拠）。**この点は変更しない。**

## 2. 本棚0件への対応（症状2）

### 2.1 状況（2026-08-17に実物HTMLで訂正）

所有者の確認: **本棚0件のときの画面は、通常の本棚新規作成画面と全く同じ。**

同期では本棚は一部分でしかないのに、**貸出も予約も読書記録も取得できなくなる**。

**当初の想定は誤っていた。** 「`select[name=otherbook]` が無いので `ShelfListParser` が失敗する」と
推測して対処したが、実物のHTMLを取得したところ**そうではなかった**。実測結果は次のとおり。

| 検査 | 実測 | 判定 |
|---|---|---|
| `select[name=otherbook]` | **存在する** | — |
| その option | **1件**（`value="0"`、ラベルは `------------------` のプレースホルダ） | — |
| `ShelfListParser` | **成功する**（`Shelf(0, "-----")` を1件返す） | 捕捉されない |
| 見出し「マイ本棚」の完全一致 | **無い**（「マイ本棚の新規作成」「本棚作成の実行」） | — |
| `input[name=otherbook]` | **無い**（selectはあるがinputは無い） | — |
| `table[summary=本棚属性]` | **無い** | — |
| `ShelfParser` | **失敗する** | ここで落ちる |

つまり `ShelfListParser` の例外だけを捕捉しても効かず、**`ShelfParser` が捕捉範囲の外で
`ParseException` を投げて同期全体が落ちていた**。診断ログでも、`mybooklist` の応答
（見出し「マイ本棚の新規作成」）を記録した直後に通信が止まっており、読書記録の取得へ進んでいない。

**教訓**: 実物を取得せずに「無いはず」と推測して分岐条件を決めた。進行指示14と同じ誤りである。

### 2.2 誤判定のリスクを避ける

「`otherbook` の select が無ければ0件」と単純化してはならない。
本棚同期は `replaceShelfSnapshot` で**全置換**するため、
**別の理由で解析できなかった画面を0件と誤判定すると、ローカルの本棚データを消す。**

新規作成画面を厳密に識別する材料（`gamenid` 等）は**未取得**である
（`docs/design/bookshelf-editing-capture-plan.md` でも「未取得」のまま）。
実測せずに識別子を推測しない（進行指示14）。

### 2.3 文脈の有無で扱いを分ける

**A. 通常同期（`fetchUserData`）— 文脈がない**

**本棚の解析に失敗した場合**、本棚の取得だけをスキップし、他のデータは通常どおり取得する。
0件と断定せず、**ローカルの本棚データは変更しない**。

**捕捉範囲は本棚解析ブロック全体とする**（§2.1の実測により訂正）。`ShelfListParser` だけを
囲んでも、実物では成功してしまい `ShelfParser` で落ちる。囲む範囲は
「一覧の解析・現在本棚の解析・他本棚への切り替えと解析」の全体である。

**捕捉するのは `ParseException` だけとする。** ネットワーク・メンテナンス・認証の失敗は
従来どおり伝播させる。これらを本棚スキップへ倒すと、通信障害を「本棚が無い」と誤読する。

- 新規アカウントの同期が通るようになる（本件の主目的）
- 本棚を誤って消す危険がない
- 代償: 実際に本棚を0件にした場合、ローカルに古い本棚表示が残る。
  §2.4の実測が済むまでの既知の制限とする

**B. 本棚削除の直後 — 文脈がある**

削除前のスナップショットで**本棚がちょうど1件だった**場合に限り、削除後の
「`otherbook` の select が無い」を**0件になったと解釈してよい**。
削除前の状態がその解釈を裏付けるためである。この場合は本棚0件として
`Applied` と裁定し、ローカルも0件へ更新する。

削除前が2件以上だったのに解析不能になった場合は、従来どおり `Unknown` とする。

### 2.4 将来の実測（本修正では行わない）

新規作成画面の識別子を実測できれば、Aでも0件と確定できるようになる。
必要なのは**本棚0件の状態で「マイ本棚」を開いたときのHTML**である。§5に記録する。

## 3. 予約の連絡方法（症状3）

### 3.1 実測で分かったこと

診断ログ（2026-08-16）より:

- 確定POST `WOpacTifDirectYoyExecAction.do` は**送信され200が返っている**
- 送信フォームは**過去に成功した3回と構造・値まで同一**（`receivename=106&contact=4`）
- その後の予約状況一覧に**対象書誌が載っていない**（成功時は載っている）
- 応答に「メールアドレスが設定されていません。別の連絡先を選択してください。」が含まれる

所有者の確認: **メールアドレスは未登録。**連絡方法のドロップダウンは「Email」と「連絡不要」の
2つで、**「連絡不要」の value は `9`**。Emailのまま確定するとダイアログでエラーになり、
OKを押すと予約確認画面へ戻る。

### 3.2 修正

`contact` を **`9`（連絡不要）**にする。所有者の判断により、
**メール登録済みのアカウントでも一律9とする**（アプリ自身が予約準備完了を通知するため、
サイトのメール通知は冗長）。

あわせて、`receivename` と同じ検証をかける。現在 `contact` だけが無検証で、
**選択肢に無い値を送って初めて失敗が分かる**状態になっている（[DirectReservationConfirmParser.kt:36]）。

- 確認画面の `select[name=contact]` の option に `9` が**存在することを確認してから送る**
- 存在しなければ**状態変更POSTを送らずに停止**し、理由を表示する

複数同時予約でダイアログに阻まれて途中経過が分からなくなる問題も、これで解消する。

## 4. テスト方針

- **本棚: 末尾以外の本棚を削除するケースを固定する。** これが今回の中心である。
  MockWebServerで、切り替えPOSTが**対象本棚番号で送られること**、
  切り替え応答のHTMLからフォームが組まれること（キャッシュHTMLではないこと）を確認する
- **切り替え後の応答が対象と一致しない場合、状態変更POSTを送らないこと**
- 本棚名変更・資料メモ更新・資料削除でも切り替えが行われること
- **同期: `otherbook` の select が無い応答で、貸出・予約・読書記録が取得できること**、
  かつ**ローカルの本棚が変更されないこと**
- **本棚1件のみの削除後に0件になった場合に `Applied` となること**、
  **2件以上から解析不能になった場合は `Unknown` のままであること**（対の関係で固定する）
- 予約: `contact=9` が送られること。**選択肢に9が無い場合にPOSTを送らず停止すること**
- 正常系のフィクスチャは**実測由来のHTML**を使う（進行指示13）。
  今回のHARから、本棚一覧・削除確認・削除後一覧のHTMLを採取して使える

## 5. 既知のリスク・未解決

- **資料追加（AddItem）がカレント依存かどうかは未検証。** `booklist` で対象を明示する別経路のため
  今回は変更しないが、同じ危険がある可能性は残る。誤登録の報告が出たら最初に疑うこと
- **本棚0件の識別子が未取得。** §2.4のとおり、通常同期では0件と確定できず、
  ローカルに古い本棚表示が残る場合がある
- **`ShelfListParser` がプレースホルダ option を本棚として返す。** 本棚0件の画面では
  `value="0"`・ラベル `------------------` の option を `Shelf(0, "-----")` として1件返す
  （§2.1の実測）。本棚番号は実際には1以上であり、明らかに正しくない。
  現状は直後に `ShelfParser` が失敗するため実害は出ていない。
  **今回は直さない**——捕捉範囲を広げるだけで症状は解消し、プレースホルダ除外は
  本棚がある正常系にも影響しうるため単独の検証が要る（進行指示7）。
  本棚まわりに次に手を入れるときに扱うこと
- サイトが `otherbook` を完全に無視しているのか、条件付きで参照しているのかは分離していない。
  修正方針（カレントを対象へ合わせる）はどちらでも成立するため、本件の判断には影響しない
