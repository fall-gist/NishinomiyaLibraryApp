公式サイトの本棚編集画面には『並び順』があり、N冊含まれる本棚では1からNまで一意の整数が割り当てられており、

## 1. 所有者による確定事項（2026-09-27）

1. 並べ替えの操作は**ドラッグ**（自動予約のルール画面と同じ操作）
2. 編集の場所は、既存の「本棚の編集」画面（本棚名・資料メモを直す画面）。1回の送信で名前・メモ・並び順をまとめて更新する
3. 公式サイトの本棚画面の並びと「並び順」の数値（以下 S）の関係は、所有者がブラウザで確認した（2026-09-27）。§4.0 を参照
4. **並べ替えをせずに名前・メモだけを直して保存したときも、編集画面に見えている順で 1〜N を振り直して送る**（案B。2026-09-27 所有者確定）

## 2. 現状（確認済み）

### 2.1 サイト側（`docs/site-research.md` §13.3・§13.9 の実測）

- 編集画面（`tiles.WSdiBookListMainte`）の `LBForm` は、資料1件につき
  `bookcmnt`（hidden・現在のメモ）→ `eachcmnt`（textarea）→ `sortno`（hidden・現在の並び順）→
  `eachsortno`（text・編集後の並び順）の4項目を繰り返す
- 入力欄 `eachsortno` を変えると、画面のスクリプト `changsortno` が hidden の `sortno` へ値を写す。
  **サーバが読むのは `sortno`**（メモの `bookcmnt`/`eachcmnt` と同じ構造。メモ編集ではこれを見落として
  反映されなかった前例がある）
- 各行の要素の id は `<項目名><tilcod>`（例: `sortno1000001654099`）。**行と資料を資料番号で対応づけられる**
- 並び順の値は棚によって `1000, 2000, …` の場合も `1, 2, …` の場合もある

### 2.2 アプリ側

- 同期（`LicsXpClient.fetchUserData`）と本棚の変更後の再取得は、本棚画面の資料を `ShelfParser` で
  **サイトの表示順（DOM順）どおり**に得ている
- しかし Room の `shelf_items` は並び順を持たず、表示は `ORDER BY shelfNo, registeredDate DESC`
  （`ShelfItemDao.kt:21`）と `sortedByDescending { it.registeredDate }`（`BookshelfScreenController.kt:77`）で
  **登録日の新しい順**になっている。**サイトの並びが失われている**
- 本棚の変更の送信後の照合（`BookshelfGateway.sameItems`）は、既に**位置ごと**に
  資料番号・書名・メモ・登録日を比べている（並び順込みの照合）。比べる項目は明示的に列挙しているため、
  列を足しても照合は変わらない

## 3. 段階1: 表示順をサイトに揃える（読み取りのみ。サイトへ書き込まない）

### 3.1 設計

- ドメインの `ShelfItem` に `position: Int`（本棚内の0始まりの位置。サイトの表示順）を足す
- `ShelfParser` が、本棚画面の資料を読むときに DOM 順の位置を入れる
- Room の `shelf_items` に `position INTEGER NOT NULL DEFAULT 0` を足す。**DB version 9 → 10**。
  マイグレーション `MIGRATION_9_10` は列の追加だけ。既存の行は 0 になり、次の同期で正しい値に置き換わる
- 表示の順を `ORDER BY shelfNo, position, registeredDate DESC` に変える。**移行直後（全行 0）の間は
  従来どおり登録日の新しい順**になり、同期後にサイトの順になる
- 画面側の並べ替え（`BookshelfScreenController.kt:77`）も `position` の昇順へ変える
- 本棚のデータを1件ずつ差し込む経路（`ShelfItemDao.insert`/`update` 等）があれば、`position` の扱いを確認する
  （全置換 `replaceShelfSnapshot` だけなら追加の考慮は不要）

### 3.2 変えないこと

- 送信後の照合の規則（`sameItems` は `position` を比べない。位置ごとに比べる現在の方式のまま）
- バックアップの形式（本棚の資料はバックアップに含まれていない。確認すること。含まれていれば既定値で読み込めること）
- `AppDatabase` の版番号の複製定数（バックアップの `sourceDbVersion` 用。`AppDatabase.kt:42` 付近）は **10 に揃える**

### 3.3 テスト

1. `ShelfParser` が資料に DOM 順の `position`（0, 1, 2, …）を入れる（実物フィクスチャ `mybooklist.html`）
2. マイグレーション 9 → 10 で既存の行が残り、`position` が 0 になる（既存のマイグレーションのテストの流儀に合わせる）
3. DAO の並び: 同じ本棚の中で `position` の昇順。`position` が同じなら登録日の新しい順
4. 同期で保存した並びが、サイトの表示順と一致する

### 3.4 手動確認

1. 同期後、アプリの本棚画面の並びが公式サイトの本棚画面の並びと一致する

## 4. 段階2: 並び順を編集する（サイトへ書き込む）

### 4.0 所有者のブラウザでの観察（2026-09-27）

- 多くの本棚は、本棚画面の並びが S の昇順になっている
- しかし**必ずしも S の昇順ではない本棚がある**（例: 2000, 3000, 4000, 5000, 6000, 9000, 3000, 5000, 7000, …）。
  所有者の推測では、書誌の出し入れを繰り返した本棚
- そのような本棚で、**S を触らずに編集画面の「編集完了」を押すと、S の昇順に並び替わる**
- **S には重複も 0 もある。S が同じもの同士は登録日の古い順**に並ぶ
- 1000 の倍数が振られている本棚が多い。アプリから書誌を加えた本棚では 1 から振られているようである

以上から、**サーバは本棚の更新（UPDATE）を受けると、S の昇順（同じ S は登録日の昇順）に並べ直す**と読める（推定）。

### 4.1 設計

- 「本棚の編集」画面の資料の一覧を、**ドラッグで並べ替えられる**ようにする
  （自動予約のルール画面 `ui/settings/AutoReservationRuleDrag.kt` と同じ操作・同じ仕組み）。
  一覧の初期の並びは段階1の `position`（サイトの表示順）
- **送信する S は、常に編集画面に見えている順の 1〜N の重複しない連番**とする（並べ替えたかどうかに関わらない。案B）。
  重複が無いので、登録日による並びの揺れが起きず、サーバが並べ直した結果が見えている順と一致する
- 送信（既存の `RemoteBookshelfMutation.EditShelf` を拡張し、希望の並び＝資料番号の列を持たせる）:
  - 編集画面の `LBForm` の資料行は、これまでどおり**直前に取得した本棚画面の DOM 順**と対応づける
    （既存のメモ編集と同じ。`requireMatches` の確認を含む）
  - **追加の安全確認**: 各行の `sortno` 要素の id が `sortno<その行の資料番号>` であることを確かめる
    （`docs/site-research.md` §13.9 の実測）。一致しない・id が無い場合は**送信せずに停止**する（`BS_EDIT_FORM`）。
    行と資料の対応を二重に確かめるためである
  - 各行の `sortno`（サーバが読む hidden）と `eachsortno`（入力欄）の**両方**に、その資料の希望の順位（1 始まり）を入れる
    （ブラウザで入力したときと同じ状態。メモで `bookcmnt` を見落とした前例に合わせる）
  - 行の DOM 順は**変えない**（行を並べ替えて送らない。値だけを変える）
  - 二段階の送信と完了の第3 POST は既存の本棚更新（UPDATE）と同じ
- 送信後の照合: 再取得した本棚の資料の**資料番号の並び**が希望の並びと完全に一致し、
  名前・メモが指定どおりで、他の本棚が変わっていなければ成功。それ以外は `Unknown`（自動で再送しない）

### 4.2 画面の見え方

- 並べ替えをしていなくても、保存すると S が 1〜N に振り直される（案B）。サイトの本棚画面の並びは、
  保存前にアプリで見えていた順のまま変わらない
- これまで S の昇順でなかった本棚は、アプリで保存すると「見えていた順」で S が揃う

### 4.3 テスト

1. 並べ替えたとき、各行の `sortno` と `eachsortno` に希望の順位が入り、行の DOM 順は変わらない
2. 並べ替えていないときも、見えている順の 1〜N が入る（案B）
3. `sortno` の要素 id が資料番号と一致しない行があれば、送信しない（状態変更の送信がゼロ件）
4. 送信後の再取得の並びが希望どおりなら `Applied`。違えば `Unknown`
5. 名前・メモの変更と並べ替えを同時に行ったとき、両方が送られ、照合も両方を見る
6. 既存の名前・メモの編集のテストが、案Bに伴う期待値の変化（S が 1〜N になる）以外は変わらない。
   **期待値を変えたテストは、変えた理由を報告すること**
7. 画面: ドラッグの並べ替えの状態（コントローラ側）を単体テストで固定する。見た目は実機確認

### 4.4 手動確認（実サイトへの書き込み。所有者が行う。テスト用の本棚で行うことを勧める）

1. 本棚の編集で資料をドラッグして並べ替え、保存 → アプリと公式サイトの本棚画面が、並べ替えた順になる
2. 公式サイトの編集画面で「並び順」が 1〜N になっている
3. 並べ替えずにメモだけ直して保存 → 並びは変わらない
4. S の昇順でなかった本棚で、並べ替えずに保存 → アプリで見えていた順のまま

## 6. 未解決・既知のリスク

1. 段階1の移行直後は、同期するまで従来の登録日順のまま表示される
2. 段階2で送る連番（1〜N）は、元の値（1000刻みなど）と形式が変わる。サイトがどちらでも受け付けるかは
   実機確認で分かる（アプリから加えた本棚で 1 から振られている観察があり、受け付けると見込む）
3. **資料の削除（`DeleteItem`）の送信後の照合は並び込みで比べている。** 削除でもサーバが S の昇順へ
   並べ直すなら、S の昇順でない本棚で資料を削除すると、削除は成立しても「結果を確認できません」になる
   可能性がある（未確認）。段階2では変えず、実機で起きたら対処する
