# 閲覧の通信を書き込みと別の列で並行に通す 設計書

作成日: 2026-09-27
状態: **実装完了・実機確認待ち**（`ff167c1`、CI run 36254702068 成功。versionName 1.10）
報告: 所有者（2026-09-26、Ver.1.8 の実機確認）。一斉予約などの処理中に書誌詳細を開くと、
1件の処理が終わるまで読み込みが待たされる。
所有者の判断（2026-09-27）: 閲覧と書き込みを分けて並行に通す。「セッション内で別の通信を割り込ませると
落ちるかもしれないが、セッションの並行は複数のブラウザで別アカウントを扱うようなもので問題ないはず。
閲覧専用のセッションを用意すれば他と干渉しないのではないか」

## 1. 現状（確認済み）

### 1.1 セッションの構成

- アプリ全体で1つの `LicsXpSession`（以下「根セッション」。`RepositoryModule.provideRootLicsXpSession`）がある
- **閲覧**（ログインしない読み取り）は根セッションを直接使う。`LicsXpClient` の `search`・`autocomplete`・
  `isLendable`・`bookDetail`・`closedDays`・`newArrivals`
- **メンバーとしての通信**（同期・予約・取消・延長・本棚の変更）は、根セッションから
  `newIsolatedSession()` で**Cookie を分けた**セッションを作って使う
- `newIsolatedSession()` は**順番待ちの仕組み（`RequestRateLimiter`）を根セッションと共有する**
  （`LicsXpSession.kt:558`）。つまり Cookie は分かれていても、**アプリ全体の通信は1本ずつ**になる

### 1.2 待たされる理由

`RequestRateLimiter` は1つの `Mutex` で通信を直列にし、開始間隔を500ms以上に保つ。
さらに `withExclusiveRequestSequence` は、確認画面の取得から確定の送信までの一連の通信の間、
この `Mutex` を持ち続ける（`LicsXpSession.kt:178`）。一斉予約では1件ごとにこの占有が起き、
その間は閲覧の通信（書誌詳細の取得）も待たされる。

### 1.3 全セッション共通の直列化の由来

`docs/site-research.md` §6（2026-07-22 のライブ検証）: 確認画面を開いてから時間を空けて確定すると
ログイン画面へ戻り予約が成立せず、再ログイン直後に確認から確定まで連続して送ると成立した。
そこで「確認から確定までを全セッション共通の排他区間で連続実行し、同期等の別要求を割り込ませない」と決めた。

**実測で分かっているのは「確認から確定までの間に時間が空くと失敗する」ことだけである。**
別のセッションの通信が**並行して**走った場合の影響は確かめていない。全セッション共通にしたのは、
同じ順番待ちに別の要求が並ぶと、予約の一連の通信が**遅れる**からである。

## 2. 設計

### 2.1 閲覧専用のセッションを分ける

閲覧に使う `LicsXpSession` を、**順番待ちの仕組みごと**根セッションから分ける。

- 新しく「閲覧セッション」を1つ作る。Cookie も `RequestRateLimiter` も**独自**に持つ
- `LicsXpClient` の閲覧の6操作（§1.1）は閲覧セッションを使う
- メンバーとしての通信（`fetchUserData`・`fetchCurrentCirculation`、予約・取消・延長・本棚の各 Gateway）は
  **従来どおり根セッションとその分離セッション**を使う。この列の直列化と占有は一切変えない

これは所有者の見立てどおり「別のブラウザでログインせずに閲覧している」状態に当たる。
閲覧の通信は予約の一連の通信と**別の列**で走るため、予約の通信を**遅らせない**
（§1.3 の失敗の原因である「時間が空く」を生まない）。

### 2.2 サイトへの負荷

- 閲覧の列の中でも、従来どおり開始間隔を500ms以上に保つ（`RequestRateLimiter` を閲覧セッション用に1つ持つ）
- 同時にサイトへ向かう通信は、最大で**2本**（閲覧の列1本＋メンバーの列1本）になる
- 新着資料の巡回（多数のGET）は閲覧の列に入る。巡回中も予約や同期が並行して走りうる

### 2.3 DI の変更

`RepositoryModule` で、根セッションとは別に閲覧セッションを提供する。区別のため Qualifier
（例: `@BrowseSession`）を付ける。`LicsXpClient` は閲覧セッションと根セッションの両方を受け取る。

- `provideLibraryGateway`（閲覧を含む）: 閲覧セッションと根セッションを渡す
- `provideCurrentCirculationGateway`: 同じく両方を渡す（`LicsXpClient` の同じクラスのため）
- 予約・延長・本棚の Gateway: 根セッションのまま（変更しない）

閲覧セッションの診断ログ（`DiagnosticLogObserver`）は根セッションと同じものを使う。

### 2.4 変えないこと

- 予約・取消・延長・本棚の変更・同期の手順、占有の範囲、送信は1回だけの規則
- `ReservationOperationGate`・`BookshelfStateGate` による操作の排他
- 閲覧の各操作の中身（URL・フォーム・解析）
- 検索の状態（検索フォーム → 結果の次のページ）は閲覧セッションの Cookie の中で完結する。
  根セッションから閲覧セッションへ移っても、検索の手順は1つのセッションの中で閉じている

## 3. テスト計画（決定論的。MockWebServer）

1. **分離の固定**: メンバーの列で `withExclusiveRequestSequence` を占有させたまま（`CompletableDeferred` で止める）、
   閲覧セッションで `bookDetail` を呼ぶと、**占有が解ける前に**結果が返る
2. **従来の直列化の維持**: メンバーの列の占有中は、別の分離セッション（別メンバー）の通信が待たされる
   （既存の挙動。既存テストがあればそれで足りる）
3. 閲覧の列の中では、開始間隔が500ms以上に保たれる（`waitForRequestSlot`・`nowMillis` を差し替えて確かめる）
4. 閲覧セッションと根セッションで Cookie が共有されない
5. DI: `LibraryGateway` の閲覧の操作が閲覧セッションへ、`fetchUserData` が根セッションの分離セッションへ
   向かう（`LicsXpClient` の単体テストで、2つのセッションを別々の MockWebServer かリクエスト記録で見分ける）

## 4. 手動確認（CIのAPKで実機。**予約を実サイトに作るため所有者自身が行う**）

1. 蔵書検索から複数件の一斉予約を始め、その最中に検索結果の書誌詳細を開く → **すぐ開く**（1件ごとに待たされない）
2. 一斉予約の結果がすべて成功している。予約中一覧と公式サイトにも反映されている
3. 同期（プル更新）の最中に書誌詳細を開く → すぐ開く
4. 通常時（処理中でない）の検索・書誌詳細・新着資料が、これまでどおり動く

## 5. 未解決・既知のリスク

1. **別セッションの並行通信が予約を妨げないことは、実測ではなく推定である**（§1.3）。手動確認の1・2で確かめる。
   予約が失敗・結果不明になった場合は、この変更を取り消す（閲覧セッションを根セッションへ戻すだけで元に戻る）
2. サイトが同一の接続元からの同時接続を制限している場合、並行した通信が拒否される可能性がある（未確認）
3. サイトへ同時に向かう通信が最大2本になる（§2.2）
