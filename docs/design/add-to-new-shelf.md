# 新しい本棚を作って追加する 設計書

作成日: 2026-09-27
状態: **段階1（通信層・ドメイン・リポジトリ）実装完了（コミット）・段階2（画面・コントローラ）未着手**
依頼: 所有者（2026-09-27）「書誌を本棚に追加する際、新しい本棚を作って追加する機能に対応させたい」
所有者の方針（2026-09-27）: サイトの「新規登録」（`999 `）の流れは辿らない。**既存の本棚作成と本棚への追加を続けて実行する**。

## 1. 確定事項（2026-09-27 所有者）

1. 「本棚へ追加」ダイアログの追加先の選択肢に「新しい本棚を作成」を加える。選ぶと本棚名の入力欄が出る。
   確認は1回で、「本棚『◯◯』を作成し、この資料を追加します」と出す
2. 一斉本棚追加（蔵書検索・新着資料・読書記録）でも使えるようにする。本棚の作成は最初に1回だけ行い、その本棚へ順に追加する
3. 途中で失敗したとき
   - 作成に成功し追加に失敗した場合: **作った本棚は残す**（自動で削除しない）。「本棚は作成したが、追加に失敗した」と知らせる
   - 作成の結果が不明（POST後に成否が確認できない）: **追加は行わずに止める**（従来の規則どおり）
   - 作成に失敗: 追加は行わない

サイトの `999 `（新規登録）は引き続き送らない（`BookshelfForms`・`BookshelfGateway` の拒否はそのまま）。

## 2. 既存の仕組み（確認済み）

- 本棚作成: `RemoteBookshelfMutation.CreateShelf` → `BookshelfGateway.create`。二段階POST。成功判定は
  「作成前と比べて増えた本棚がちょうど1つで、その名前が入力どおり、既存の本棚は不変」（`BookshelfGateway.kt` の `create`）。
  メンバーの本棚が0件でも作成できる（`docs/design/bookshelf-create-from-empty.md`）
- 資料の追加: `RemoteBookshelfMutation.AddItem(shelfNo, tilcod, memo, expected)`
- 一斉追加: `BookshelfRepository.addItems(request, onProgress)`。`BookshelfStateGate` とログインを全体で1回だけ取り、
  1件ずつ追加する。`Unknown`・`Failure` で打ち切り、残りは `NotAttempted`（`docs/design/bulk-bookshelf-add.md`）
- 成功のたびに `replaceShelfSnapshot` で Room を置き換える

## 3. 設計

### 3.1 通信層（`BookshelfGateway`）

- 作成に成功した結果（`RemoteBookshelfOutcome.Applied`）に、**新しく作られた本棚の番号**を載せる
  （例: `createdShelfNo: Int? = null`。作成以外では null）。値は成功判定で使っている「作成前と比べて増えた本棚」の番号そのものとする
- それ以外の手順・照合は変えない

### 3.2 ドメイン・リポジトリ

一斉追加の要求を、追加先として「既存の本棚」と「新しい本棚」のどちらも表せるように広げる。

- 追加先: 既存の本棚（本棚番号）か、新しい本棚（本棚名）
- 要求にメモを持たせる（単件の追加はメモあり、一斉追加は従来どおり空文字）
- 新しい本棚のときの確認時の期待値: メンバー名と、そのメンバーの本棚の数（作成の照合に使う。対象の本棚は無い）

`addItems` の処理（ゲートとログインは全体で1回。既存どおり）:

1. 追加先が新しい本棚なら、まず `CreateShelf(name, 確認時の期待値)` を送る
   - `Applied`（`createdShelfNo` あり）: Room を置き換え、以降の追加先をその番号にする。
     追加の期待値は「メンバー名・本棚の数 = 確認時 + 1・対象の本棚 = (新しい番号, 入力した名前, 資料0件)」
   - `Applied` だが `createdShelfNo` が無い: 起きない想定だが、結果不明として扱い、止める
   - `Unknown`: 止める。資料は全件 `NotAttempted`
   - `Failure`: 止める。資料は全件 `NotAttempted`
   - 例外: `Failure` と同じ扱い（理由は既存の `toFailureReason`）
2. 以降は既存の一斉追加と同じ（1件ずつ追加。期待値は直前の結果から資料数だけ更新）

結果に、作成の結果を加える（追加先が既存の本棚なら「作成なし」）:
作成した（本棚番号）／結果不明／失敗（理由）。

### 3.3 画面・コントローラ（`BookshelfEditingUiController`、`BookshelfScreen`）

- 単件・一斉のダイアログの本棚の選択肢の末尾に「新しい本棚を作成」を加える。選ぶと本棚名の入力欄（50文字以内。
  既存の `isValidShelfName`・`shelfNameError` を使う）が出る。既存の本棚を選び直したら入力欄は消える
- メンバーを選んで本棚の一覧を読み込むまでは、「新しい本棚を作成」も選べない（既存の本棚と同じ）
- 確認:
  - 単件: 「本棚『◯◯』を作成し、この資料を追加します」＋書名・メモ。確定ボタンは「作成して追加」
  - 一斉: 「本棚『◯◯』を作成し、N件の資料を追加します」
- 確定の直前の再確認（既存の一斉追加と同じ考え方）: メンバーの存在と名前、本棚の一覧を読み込み済みであること、
  本棚の数が確認時と同じこと（変わっていたら「本棚の状態が変わりました。もう一度選択してください」）
- 送信は既存の一斉追加の経路（`addItems`）を使う。単件も1件の一斉追加として送る。処理中の帯・排他は既存どおり
  （作成の間は進捗「0件目/N件」のままでよい）
- 結果:
  - 単件: 1つの結果ダイアログ。作成と追加の結果を合わせた文言（§4）
  - 一斉: 既存の結果の一覧の先頭に、作成の結果の行を1行加える

## 4. 結果の文言

| 作成 | 追加 | 単件の文言（例） | 種別 |
|---|---|---|---|
| 作成した | 追加した | 本棚『◯◯』を作成し、資料を追加しました | 成功 |
| 作成した | 既に登録済み | 本棚『◯◯』を作成しました。資料は既に登録済みでした | 注意 |
| 作成した | 結果不明 | 本棚『◯◯』は作成しましたが、資料の追加結果を確認できませんでした（同期して確認） | 注意 |
| 作成した | 失敗 | 本棚『◯◯』は作成しましたが、資料を追加できませんでした（理由） | 失敗 |
| 結果不明 | 送信せず | 本棚を作成できたか確認できませんでした。資料は追加していません（同期して確認） | 注意 |
| 失敗 | 送信せず | 本棚を作成できませんでした（理由）。資料は追加していません | 失敗 |

一斉の先頭行: 「本棚『◯◯』を作成しました」／「本棚を作成できたか確認できませんでした」／「本棚を作成できませんでした（理由）」。
資料の行は既存の文言（作成に失敗・不明のときは全件「送信していません」）。
理由の言い回しと再試行・確認の案内は、既存の `BookshelfEditingContentBuilder` の規則に合わせる。

## 5. テスト（決定論的）

- 通信層: 作成の `Applied` に新しい本棚の番号が載る（既存本棚あり・0件の両方）
- リポジトリ:
  1. 新しい本棚 + 2件: 作成 → 追加2件。2件目の期待値は本棚の数 +1・新しい番号・資料数更新
  2. 作成 `Unknown` → 追加を送らない、全件 `NotAttempted`、作成は結果不明
  3. 作成 `Failure`・例外 → 追加を送らない
  4. 作成成功・1件目の追加 `Failure` → 本棚は削除しない（削除の要求を送らない）、残りは `NotAttempted`
  5. 既存の本棚への一斉追加は従来と同じ結果（回帰）
  6. メモが単件の追加で送られる
- コントローラ: 選択肢の切り替え、本棚名の検証、確認の文言、確定前の再確認（本棚の数の変化・メンバー名の変化）、
  結果の文言（§4 の各行）、処理中は受け付けない

## 6. 手動確認（CIのAPKで実機。**実サイトに本棚を作るため所有者が行う**）

1. 書誌詳細から「新しい本棚を作成」で追加 → アプリと公式サイトに新しい本棚ができ、資料が入っている
2. 蔵書検索・新着資料・読書記録から複数件を「新しい本棚を作成」で追加 → 同上
3. 本棚を1つも持たないメンバーでも作成して追加できる
4. 確認後に戻る・名前が空・51文字以上 → 送信されない
5. 試した本棚は、確認後に所有者が削除する
