# 読書記録の検索を単語AND検索にする 設計書

作成日: 2026-09-20
状態: **設計確定・実装待ち**
報告: 所有者（2026-09-20）「読書記録のテキスト検索はおそらく完全一致になっている。部分一致に変えたい。
スペース区切りの複数単語はAND検索として、いずれの単語も名前に含まれる書誌がヒットするようにしたい」

## 1. 現状（確認済み。所有者の見立てを一部訂正する）

**完全一致ではない。すでに部分一致である。**

- `ReadingRecordDao.search` は `titleNormalized LIKE '%' || :normalizedQuery || '%'`
  （`ReadingRecordDao.kt:41` 付近）であり、部分一致で照合している
- ただし入力は `TextNormalizer.normalize`（`Models.kt`）を通る。これは NFKC 正規化・小文字化に加えて
  **空白をすべて削除する**
- そのため「ゾロリ 王子」と入力すると `ゾロリ王子` という1つの連続した文字列として照合され、
  「ゾロリ」と「王子」の両方を含む記録（間に他の文字が挟まるもの）は**ヒットしない**

つまり、所有者が「完全一致のようだ」と感じた原因は、照合の方式ではなく**空白の潰し方**にある。
今回直すべきは、空白を区切りとして扱い、語ごとのAND条件にすることである。

保存側も `titleNormalized`（同じ正規化を通した列）を持っている。空白を潰す正規化自体は、
表記ゆれ（全角・半角、空白の有無）の吸収に役立っているため**やめない**。

## 2. 確定仕様

1. 入力を**半角空白・全角空白で区切って単語に分ける**。連続した空白は1つの区切りとして扱う
2. 各単語を現行と同じ `TextNormalizer.normalize` で正規化する（空白はもともと除去されるため、
   区切りは分割の時点で失われる）
3. **すべての単語を含む**記録だけを残す（AND）。含まれる位置は問わない（部分一致）
4. 対象は**書誌名のみ**（現状と同じ）。読書記録は著者名を保持していない
5. 空の入力、空白だけの入力は「検索なし」として全件を出す（現状と同じ）
6. 並び順・メンバー絞り込み・履歴未有効化の案内（`showActivationHint`）は変えない

## 3. 設計

### 3.1 絞り込みをRoomからメモリへ移す

可変個のAND条件を Room の `@Query` では書けない（語数が固定でないため）。取りうる案は2つある。

**案A（採用）: 全件を購読し、純関数で絞り込む。**
`ReadingRecordRepositoryImpl.search` を `records(memberId)` の購読＋フィルタに変える。
- 読書記録は既に「検索していないとき全件を読み込んで一覧に出す」作りであり、
  全件をメモリに載せること自体は現状と変わらない。新たな負荷は語ごとの文字列照合だけである
- 新着資料の絞り込み（`NewArrivalsContentBuilder.build`）が既に同じ流儀で、前例がある
- 純関数にできるため、決定論的な単体テストで仕様を固定できる

**案B（不採用）: `@RawQuery` で語数ぶんの LIKE を動的に組む。**
DB側で絞れるが、動的SQLの組み立てが増える。語は引数としてバインドすれば安全だが、
本件の規模（家族の履歴。数千件程度）では案Aで十分であり、単体テストも書きやすい。

### 3.2 純関数を追加する

`domain/model/Models.kt` の `TextNormalizer` の近くに置く（読書記録以外からも使えるようにするため、
読書記録専用の名前にしない）。

```kotlin
/** 空白区切りの検索語。すべての語を含むものだけを残す(AND)。 */
object KeywordQuery {
    /** 入力を空白(半角・全角)で分割し、正規化した語の一覧を返す。空白のみの入力では空リスト。 */
    fun terms(query: String): List<String>

    /** [terms]がすべて[target]（正規化済みでなくてよい）に含まれるか。語が空なら常にtrue。 */
    fun matches(target: String, terms: List<String>): Boolean
}
```

`matches` は `target` を `TextNormalizer.normalize` してから `contains` で判定する。

### 3.3 変更の範囲

| ファイル | 変更 |
|---|---|
| `domain/model/Models.kt` | `KeywordQuery` を追加 |
| `data/repository/ReadingRecordRepositoryImpl.kt` | `search` を全件購読＋`KeywordQuery` の絞り込みに変える |
| `data/local/dao/ReadingRecordDao.kt` | `search` は**残す**（§3.4） |
| UI・Controller | **変更しない**。`ReadingRecordsScreenController` は `search` を呼ぶだけで、規則は Repository 側にある |

### 3.4 DAOの `search` を残す理由

アプリからは呼ばれなくなるが、次の理由で残す。

- `LocalDataTest`（`:607` 付近）が、保存時に `titleNormalized` が正しく作られることを
  このメソッド経由で確認している。消すと、正規化列の担保が無くなる
- 列 `titleNormalized` 自体を消すと Room のマイグレーションが必要になる。割に合わない

KDoc に「現在アプリからは使っていない。`titleNormalized` の担保としてテストから使う」と明記する。

### 3.5 スコープ外

- 新着資料の絞り込み（`NewArrivalsContentBuilder`）も現在は単語AND ではないが、**今回は変えない**。
  必要なら所有者に確認のうえ別途扱う
- 蔵書検索（公式サイトへの問い合わせ）は変えない
- 読書記録画面の複数選択（第3段階）とは独立した改修である

## 4. テスト計画（決定論的）

`KeywordQuery`（純関数）:

1. 空文字・空白のみ → 語は空。`matches` は常に true
2. 1語 → 部分一致する（「ゾロリ」で「かいけつゾロリの大金もち」がヒット）
3. 2語のAND → 両方含むものだけヒット。順序は問わない（「ゾロリ 大金」「大金 ゾロリ」のどちらでも）
4. 片方しか含まないものはヒットしない
5. 全角空白での区切り、半角と全角の混在、連続した空白
6. 全角英数と半角英数の同一視（「ＡＢＣ」と「abc」）、大文字小文字の同一視
7. 対象側に空白が含まれる場合（「ＡＢＣ　著者」に対して「abc 著者」がヒットする。現行の挙動を維持）

`ReadingRecordRepositoryImpl`（フェイクDAO）:

8. 検索語が空なら `records` と同じ結果を返す
9. 2語のAND で、メンバー絞り込みと併用しても正しく絞れる
10. 並び順（`loanDate` の新しい順、同日は `title` 昇順）が保たれる

既存テストは期待値を変えずに通るはず。**通らなくなった場合は、テストを書き換える前に実装を疑うこと。**

## 5. 手動確認（CIのAPKで実機）

1. 1語で検索 → 書誌名の途中に含まれるものもヒットする
2. 2語をスペースで区切って検索 → 両方を含むものだけがヒットする
3. 語の順序を入れ替えても同じ結果になる
4. 全角スペースで区切っても同じ結果になる
5. 検索欄を空にすると全件に戻る
6. メンバーを選んだ状態で検索すると、そのメンバーの記録だけが対象になる

## 6. 未解決・既知のリスク

1. 記録が非常に多い場合、語ごとの照合をメモリで行う負荷が増える。ただし全件の読み込みは現状も
   行っており、増えるのは文字列照合だけである。実機で遅さを感じたら案B（`@RawQuery`）へ移す
2. 「名前に含まれる」の対象は書誌名のみである。著者名では検索できない（記録が著者を持たないため）
