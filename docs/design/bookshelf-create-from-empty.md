# 本棚0件のメンバーで本棚を作成できない不具合 設計書

作成日: 2026-09-26
状態: **設計確定・実装待ち**
報告: 所有者（2026-09-26、Ver.1.8 の実機確認中）。メンバー3人のうち、本棚を1つも持たない3人目で
本棚を作成すると「図書館サイトの表示が変更された可能性があるため、安全に停止しました。
自動では再試行しません　診断コード: BS_PARSE_EXCEPTION」で止まる。

## 1. 原因（コード読解と実物HTMLによる。実機ログは見ていない）

本棚の変更操作は、どれも最初に `fetchAllShelves()`（`BookshelfGateway.kt:388`）で全本棚を取得し、
期待値と照合してから送信する。

本棚0件のアカウントで「マイ本棚」を開くと、サイトは**本棚の新規作成画面**を返す
（`docs/design/account-and-bookshelf-fixes.md` §2.1 の実測。実物は `fixtures/mybooklist_empty.html`）。
この画面では `ShelfParser` が失敗し、`ParseException` が `mutate()` の捕捉（`:104`）まで上がって
`BS_PARSE_EXCEPTION` になる。

**同期（`fetchUserData`）は Ver.1.2 で0件に対応済みだが、本棚の作成は対応していなかった。**
`account-and-bookshelf-fixes.md` の表題は「同期・本棚作成が失敗する」だが、実際に直したのは
同期（§2.3 A）と削除直後（同 B）だけである。**0件から最初の本棚を作る経路は、これまで一度も
通っていない。**

**サイトへの書き込みは送っていない。** 失敗しているのは送信前の取得の段階である。

## 2. 設計

### 2.1 0件と判断してよい条件（誤判定の防止）

`account-and-bookshelf-fixes.md` §2.2 のとおり、解析できない画面を安易に0件とみなすと、
別の理由で壊れた画面を0件と誤読する。そこで**文脈がある場合に限り**0件と判断する（同 §2.3 B と同じ考え方）。

次の**すべて**を満たすときだけ、本棚0件のスナップショットとして扱う。

1. 操作が**本棚の作成**（`RemoteBookshelfMutation.CreateShelf`）である
2. 期待値の本棚数が **0**（`expected.shelfCount == 0`。アプリも0件と認識している）
3. 取得した画面で `ShelfParser` が失敗する
4. 同じ画面から `BookshelfCreateFormParser` が**成功する**（`listname`・`commnt` を持つ作成フォームがある）
5. `ShelfListParser` の結果が、プレースホルダ（`value="0"`）だけである

いずれかを欠けば、従来どおり `ParseException` として停止する。作成以外の操作では一切変えない。

### 2.2 作成の手順（0件のとき）

通常の作成は、本棚一覧の画面から入力画面へ移り（`WOpacSdiBookListToInputAction.do`）、
入力画面の作成フォームを使う。**0件の画面はそれ自体が作成画面**であり、同じ `LBForm` に
`listname`・`commnt` があり、送信先も同じ `WOpacSdiBookListExecAction.do` である（実物HTMLで確認済み）。

したがって0件のときは、**入力画面への移動を省き、0件の画面そのものの作成フォームを使う**。
そこから先の二段階の送信（確認画面の検証、確定の送信、送信後の再取得と照合）は通常の作成と同じ
`twoStage` を通す。フォームの値はブラウザが送るものと同じ（画面にある項目をそのまま、名前だけ差し替える）。

### 2.3 送信後の照合

送信後の再取得で、本棚が**ちょうど1件**あり、その名前が指定どおりであれば成功とする。
これは通常の作成の成功条件（新しい本棚が1件増え、既存の本棚は変わらない）の、既存0件の場合に当たる。
それ以外は、既存の規則どおり `Unknown`（結果を確認できない。自動で再送しない）とする。

### 2.4 診断情報に解析失敗の画面を載せる（所有者の依頼）

いまの `BS_PARSE_EXCEPTION` は、どの画面で解析に失敗したかを捨てている。`ParseException` と
`LibraryError.Parse` は `screen`（固定の識別子。例: `shelf`）と `reason`（コード内の固定文言）を
持っているので、これを残す。

- 利用者に見せる診断コード: `BS_PARSE_EXCEPTION`（`shelf`）のように、**画面の識別子を括弧で添える**
- 診断ログ（`noteDiagnostic`）: 画面の識別子と理由の文言を両方残す
- いずれもコード内の固定文字列であり、利用者の情報やサイトの応答本文は含まない

## 3. テスト計画（決定論的。MockWebServer と実物由来のフィクスチャ）

1. 本棚0件（`mybooklist_empty.html`）で作成すると、入力画面への移動を送らず、0件の画面の作成フォームで
   二段階の送信が行われる。送信するフォームの `listname` が指定の名前である
2. 送信後の再取得で本棚が1件・名前一致なら `Applied`
3. 送信後の再取得で本棚が0件のまま、または名前が違うなら `Applied` にしない
4. **期待値の本棚数が0でない**のに0件の画面が返ったら、送信せず停止する（誤判定の防止）
5. **作成以外の操作**（資料の追加・削除、本棚の編集・削除）で0件の画面が返ったら、従来どおり停止する
6. 0件の画面に作成フォームが無い（改変したHTML）なら、送信せず停止する
7. 解析失敗の診断コードに画面の識別子が付く。診断ログに画面の識別子と理由が残る
8. 既存の本棚がある場合の作成は、従来どおりの手順（入力画面への移動を含む）で送られる

## 4. 手動確認（CIのAPKで実機。**実サイトへの書き込みを伴うため所有者自身が行う**）

1. 本棚0件のメンバーで本棚を作成 → 作成でき、本棚画面に表示される
2. 公式サイトで、そのメンバーに本棚が1件できている
3. 既に本棚があるメンバーでの作成が、従来どおりできる

## 5. 未解決・既知のリスク

1. 0件の画面の作成フォームで送ったときのサイトの応答（確認画面）が、通常の作成と同じ形かは
   **未実測**である。形が違えば確認画面の検証で止まり、書き込みは送らない（安全側に止まる）
2. `ShelfListParser` がプレースホルダを本棚として返す既知の問題（`account-and-bookshelf-fixes.md` §5）は、
   今回の判定条件5で利用するだけで、直さない
