既存の予約安全策とも整合している。実装着手前に**設計書を修正すべき項目が5点**、**実装順序を変える項目が2点**、
**簡素化できる項目が2点**、**新規に仕様追加となる項目が1点**ある。所有者判断により**対応しないと確定した項目が3点**ある。

## R1. 【必須】取消済み行を「予約中」と誤判定し、資料が永久に除外される

**確認済み（欠陥）**。設計§6.2は除外根拠を「取得できた一覧に同じ`tilcod`が存在すれば家族共通の除外根拠にする」と
書いており、**予約状態を参照していない**。しかし`docs/handoff.md`「取消後の一覧仕様の確定と判定の改訂（2026-07-28）」で
実測確定したとおり、**実サイトは取消しても対象行を一覧から消さない**。予約状態列が「取消」になり、取消ボタン
(`yoykCancel`)が消えて「非表示」ボタン(`yoykHihyoji`)が置かれるだけである。

このまま実装すると次が起きる。

1. 自動予約が誤検出 → 利用者が予約一覧から手動取消
2. その行は`state=CANCELLED`として一覧に残り続ける
3. 次回以降の自動予約が「一覧に`tilcod`がある」＝予約中とみなして除外
4. **一度取り消した資料は二度と自動予約されない**（アプリは「非表示」送信を実装していない。handoff.md参照）

### 修正内容

- 除外判定は`ReservationState`を参照し、`CANCELLED`の行を除外根拠から**外す**。
- 同一`tilcod`が「予約中1行＋取消1行」で重複する既知ケース（handoff.md「同一tilcod重複という設計欠陥の発覚と対応」）が
  ここにも効く。**取消済みでない行が1件でもあれば除外**、取消済み行しか無ければ**除外しない**、という規則で書く。
- `IN_TRANSIT`・提供可能は従来どおり除外根拠に含める（サマリにも計上される予約である）。
- 貸出一覧側には同種の問題は無い。

### テスト

- 対象`tilcod`が取消済み行だけで存在する場合に候補として残ること
- 予約中1行＋取消1行の重複時に除外されること
- `IN_TRANSIT`・提供可能で除外されること

## R2. 【必須】12時間の鮮度抑止と自動予約の関係が未定義

**確認済み**。`NewArrivalsScreenController.shouldAutoRefresh`（`AUTO_REFRESH_FRESHNESS_THRESHOLD_MILLIS` = 12時間）は、
最終取得から12時間以内なら**新着巡回自体をスキップ**する。設計§8.1は`SCREEN_AUTO`をトリガーに挙げるだけで、
この既存の抑止との関係を規定していない。どちらに倒しても不都合が出る。

- 抑止を維持 → 再試行可の制御記録（`ALL_MEMBERS_LIMITED`・`ALL_MEMBERS_PRE_SUBMIT_FAILED`・`SETTINGS_MISSING`）が
  画面経由では処理されない
- 抑止を外す → アプリ起動のたびに28ジャンル約15秒の巡回＋全メンバーのログインが走る

### 修正内容

鮮度抑止は維持する。そのうえで`NewArrivalUpdateCoordinator`の責務を**取得（fetch）と評価（evaluate）に分離**し、
**新着取得をスキップした場合でも、既存キャッシュに対する再試行可候補のevaluateだけは実行する**。

`docs/spec.md` §3.11は「新着取得に**失敗**した場合は予約処理へ進まない」としか定めておらず、「鮮度によるスキップ」は
規定していないため、この扱いは要件変更にあたらない。設計書へ次を明記すること。

- 取得失敗（例外）→ evaluateへ進まない（従来どおり）
- 取得スキップ（鮮度内）→ 取得済みキャッシュに対してevaluateを実行する
- 取得成功 → 全置換後にevaluateを実行する（従来どおり）

排他（§8.2の`Mutex.tryLock()`）はfetchとevaluateを合わせた全体に掛けたままとする。

### テスト

- 鮮度内のSCREEN_AUTOで新着GETが0回、かつ再試行可候補の評価が行われること
- 取得例外時はevaluateが呼ばれないこと

## R3. 【必須】「不完全な予約一覧」の不在証明としての扱いが未定義

**確認済み**。設計§6.2は「取得できた一覧に同じ`tilcod`が存在すれば家族共通の除外根拠にする」という**陽性証拠**の
扱いだけを書いている。**不完全な一覧に対象が無いこと**を「予約していない」の根拠に使ってよいかが未定義であり、
このまま実装すると暗黙に「不在＝未予約」として扱われる可能性が高い。既存の完全性ガード
（`summaryReservationCount == 取消済みでない行数`）が偽になる状況は実在する。

### 修正内容

設計書へ次を明記する。

- 一覧が**不完全なメンバーは、その回の予約先候補から外す**（家族内重複を許容しない側へ倒す）
- 不完全な一覧の陽性一致（対象`tilcod`が実際に見つかった）は除外根拠として**使ってよい**
- 不完全な一覧の陰性（見つからない）は**不在証明に使わない**
- 全メンバーが不完全な場合、その回は予約せず再試行可として終了する

### テスト

- `complete=false`のメンバーが予約先候補から外れること
- `complete=false`でも陽性一致は除外根拠になること

## R4. 【必須】`PREPARED`の粒度がメンバーをまたぐ

**確認済み**。制御記録`auto_reservation_controls`の主キーは`tilcod`のみで、`PREPARED`は「この資料についてPOST済みか
不明」までしか表せない。メンバーAが**上限超過という確定した拒否**を返し、メンバーBへ移る途中でプロセスが停止すると、
`PREPARED`残存 → 次回`UNKNOWN_AFTER_POST` → 2か月再送禁止となる。**誰の予約も成立していないのに恒久スキップ**になる。

設計§15はこれを「取り逃しの許容」として一括りにしているが、Aの結果が確定拒否である以上、Aについて成否不明は
存在しない。粒度不足による過剰な取り逃しであり、受容の必要がない。

### 修正内容

制御記録へ**「最後に結果が確定した試行メンバー」を1列追加**する（`lastSettledMemberId`等）。

- メンバーの試行結果が確定（`RESERVATION_LIMIT_EXCEEDED`、POST前失敗など次順位へ進める結果）した時点で更新する
- 次の試行の`PREPARED`を書く前に確定済みメンバーを記録しておく
- 再開時は「確定済みメンバーの次」から再開してよい。`PREPARED`が残っていても、確定済みメンバーより後の
  未送信メンバーが存在するなら、資料全体を`UNKNOWN_AFTER_POST`へ倒さない
- 確定済みメンバーが最後の1人だった場合、および記録が無い場合は従来どおり`UNKNOWN_AFTER_POST`へ倒す

カラム1本で解ける。Room v7→v8マイグレーションの中に含める。

### テスト

- 上限超過確定→中断→再開で、次順位メンバーから再開されること
- POST直後の中断（確定メンバー記録なし）では`UNKNOWN_AFTER_POST`へ倒れ、再送されないこと

## R5. 【仕様追加】予約一覧に「送信時に指定した受取館」を表示する

**所有者判断（2026-07-29）**。既定館(`default_calendar_library`)の保存キー・共用方針は**変更しない**。
代わりに、想定外の館で予約が送信されていた場合に利用者が実サイトで修正できるよう、**アプリの予約中一覧へ
「予約送信時に指定した受取館」を表示する**。

前提として所有者から次の事実が提供された。

- 実サイトの予約一覧では、受取館はドロップダウンで**変更可能**である（**未検証**：アプリからは観測していない）
- 現在のアプリの予約一覧は、順番待ち（割当前）の行を「受取館未定」で固定表示している
  （`docs/handoff.md`「既知のハマりどころ」: 割当前は全館名が並ぶため空として扱う）
- 既定館以外での送信も、受取館の変更も、実運用ではごく稀と見込まれる。**アプリからの受取館変更機能は不要**

### 設計上の注意（必ず守ること）

1. **サイト由来の値とアプリ記録値を混同させない。** 表示は「送信時の指定館」であることが分かる文言にする。
   サイト側で利用者が受取館を変更した場合、アプリの記録は古くなる。断定的に「受取館: ○○」と出すと誤情報になる。
2. **サイトが受取館を確定表示している行では、サイトの値を優先する。** アプリ記録は割当前（現在「未定」と
   表示している行）の補完にのみ使う。
3. **行の同一性キーは`memberId + tilcod`とする。** `reservations`テーブルは同期のたびにメンバー単位で
   入れ替えられ、`id`は安定しない（`ReservationDao.deleteForMember` + `insertAll`、`id`は自動採番）。
   `reservations`へカラムを足すと同期で消えるため、**別テーブルで保持して表示時にマージ**する。
4. **記録するのは`Success`が確定した送信だけ**とする。`AlreadyReserved`は別経路で入れた既存予約であり、
   今回指定した館が反映されているとは限らない。`Unknown`は送信の成否自体が不明であり、成立していれば
   指定館は有効だが、記録して表示すると「成否不明」を「予約済み」と誤読させる。`Unknown`の扱いは
   設計者が判断し、記録するなら表示側で成否不明と区別できることを条件とする。
5. **記録は手動予約・自動予約の両方で行う。** 記録の生成点は`ReservationSubmissionResolver`の直下が自然である
   （R8の抽出と同じ段階で入れられる）。
6. **掃除**: 対象`tilcod`が予約一覧から消えた（`CancelledAndHidden`相当）行の記録は削除する。R1の取消済み行が
   残る仕様があるため、`CANCELLED`になっただけでは削除しないか、削除しても表示に影響しないことを確認する。

### spec改定

`docs/spec.md` §3.10（予約）または §3.4相当の予約一覧表示へ、次を追記する。

- 予約送信時に指定した受取館をローカルに記録し、サイトが受取館を確定していない行では「送信時の指定館」として
  表示する。サイトが確定した値がある場合はそちらを優先する
- アプリから受取館を変更する機能は設けない（実装しないことの確定）

### テスト

- 割当前の行にアプリ記録の館が「送信時の指定」として出ること
- サイトが受取館を確定している行ではサイト値が出ること
- 同期で`reservations`が入れ替わっても記録が消えないこと
- 記録が無い割当前の行は従来どおり「未定」表示になること

## R6. 【仕様変更】端末通知へ件数を入れる

**所有者判断（2026-07-29）**。設計§9.3および`docs/spec.md` §3.11は「詳細を含めず『自動予約を実行した』旨だけ」と
していたが、これでは成功2件の回と全件エラーの回が同じ文面になり、アプリを開くまで区別できない。

**成功・見送り・エラーといった一瞥で確認できる区分は通知に含めてよい。**

### 修正内容

- 通知本文に**件数の内訳**を含める（例:「自動予約を実行しました（成功2件／見送り3件）」）
- **書名・メンバー名・個別の資料情報は引き続き含めない**
- 個別ルールOFFによる見送りだけの回は従来どおり通知しない
- `docs/spec.md` §3.11「設定・結果表示・通知」の該当文を改定する

### テスト

- 通知本文に書名・メンバー名が含まれないこと（既存のテスト方針を維持）
- 件数内訳が結果分類と一致すること

## R7. 【実装順序】利用状況取得は最初から分離セッションにする

**指摘（推定を含む）**。設計§6.1は「予約用ログインセッションで貸出・予約一覧を読み、そのまま直接予約へ進む」を採用し、
「未検証なのでライブ診断で確認し、成立しなければ分離へ倒す」という順序を採っている。**この順序を逆にすべきである。**

理由（**確認済み**の事実に基づく）:

- この機能で唯一「実サイトでの予約成立が確認済み」の資産は、現行の予約遷移列である
  （`WOpacInitLoginActiontemp.do` → `WPwdLoginCheckAction.do` → `WOpacMsgNewListToTifTilDetailAction.do`
  → Disp → Exec）。ここへ到達するまでに10回以上のライブ診断を要している
- 「画面遷移状態に依存して確定POSTが詳細検索画面へ差し戻される」問題は実際に起きており、`EsTif`系の直接予約は
  それが理由で捨てている（handoff.md「通常書誌コンテキストへの予約導線変更」）
- 予約セッションへ`usrlend`/`usrrsv`のGETを挟むことは、同じ構図の再演リスクを負う

### 修正内容

- 段階4では**最初から分離セッション**（既存`LicsXpClient.fetchUserData`と同じ実績のある読み取り経路）で
  利用状況を取得する。予約セッションは成立済みの遷移列を**1バイトも変えない**
- `CurrentCirculationSnapshotSource`を`LicsXpReservationSession`へ実装する案は**保留**とし、
  統合は「通信削減の最適化」として機能が実サイトで通ったあとに別途ライブ診断で検討する
- 家庭内利用・メンバー数人規模では追加ログインのコストは許容範囲である（500ms間隔は維持）

設計§15の同趣旨のリスク記述は、この方針に合わせて「分離が既定、統合は将来の最適化」と書き換えること。

## R8. 【実装順序】`ReservationSubmissionResolver`抽出は単独で完結させる

**指摘**。設計§12の段階5は、402行の`ReservationCartRepositoryImpl`から**実サイト検証済みのロジックを剥がす**作業であり、
本機能で最も回帰リスクが高い。設計は「抽出前後で既存テスト結果が同一であること」を条件にしているが、これに加える。

- 段階5を**単独のコミット**とし、自動予約側の他の段階と混ぜない
- ユニットテスト同一性に加えて、**手動予約（カート確定・即時予約）の実機確認**まで済ませてから段階6へ進む
- 実機確認は既存の運用どおりCIのAPKで行い、HEAD SHA・操作・対象・期待値・実測値を記録する

## R9. SCHEDULED経路の利用状況二重取得を避ける

**指摘（任意だが推奨）**。設計§8.3の実行順は`syncAll(SCHEDULED)` → 新着更新 → 候補があれば全メンバーの利用状況取得
であり、**数秒前に`syncAll`が取得したばかりの予約・貸出をもう一度取得する**ことになる。

R7で分離セッションを採るなら、SCHEDULED経路では`syncAll`の結果（Room）を「直前取得」とみなして再利用してよい。
条件は「同一実行内で、そのメンバーについて完全に取得できているか」だけである。SCREEN_AUTO・SCREEN_MANUAL経路は
従来どおり取得する。

あわせて実装上の注意: 現行`SyncWorker`は`syncAll`の結果だけで`Result.retry()`を最大2回返す
（`syncWorkerDecision(result, runAttemptCount)`）。新着更新と自動予約を同じ`doWork`へ載せるなら、設計§8.3が
意図する「`PREPARED`永続化後は再試行しない」を満たすため、この関数の入力を変える必要がある。

## R10. 直近履歴を2テーブル→1テーブルにする

**指摘（任意だが推奨）**。`auto_reservation_latest_run`（固定`id=1`）と`auto_reservation_latest_items`は、
保持するのが「報告対象がある直近1回だけ」であり、SQL検索にも使わない（設計§4.2自身が「JSON文字列で保持」と
書いている）。1テーブル・1行・JSON1カラム＋確認済みフラグで足り、run削除時のitems掃除という整合の手間が消える。
v8のテーブル数を5→4に減らせる。

判定に使う状態をJSONへ入れないという設計§4.2の原則は維持すること（制御記録は別テーブルのまま）。

## R11〜R13. 対応しないと確定した項目

将来の再議論を避けるため、**設計書へ「検討したうえで採用しない」と理由込みで残すこと**。

### R11. 初回ON時の大量予約（プレビュー・1回あたりの実行上限）

レビュー時に、制御記録が空の状態でONにすると新着キャッシュ全件が候補になり、緩いキーワードで一度に多数の予約が
成立し得ると指摘した。**所有者判断で対応しない。**

理由（所有者）: 実運用上そこまで多数の該当を想定していない。予約枠は常態として大半が埋まっている。
新着資料は現状高々40件程度である。

したがって`docs/spec.md` §3.11の「アプリ独自の予約冊数上限は設けない」「現在の新着資料とのプレビューは設けない」は
**変更しない**。

### R12. ローカル予約カートを除外条件に加える

レビュー時に、手動でカートへ積んで確定待ちの資料を自動予約が別メンバーで先に取ると、その後の手動確定が
`AlreadyReserved`になると指摘した。**所有者判断で対応しない。**

理由（所有者）: 「このメンバーで取りたい」という意図はそもそも存在しない。また、手動でカートへ入れているという
ことは新着書誌の存在に気付いているのであり、「気付いていなくても取り急ぎ待ち順位を高くするため予約を入れる」
という自動予約の趣旨からして問題にならない。

除外条件は`docs/spec.md` §3.11のとおり「予約中・貸出中・読書記録・制御記録」の4つのままとする。

### R13. ルール順位固定による下位ルールの飢餓

**指摘のみ・仕様どおり**。全メンバーが上限に達している期間、上位ルールの候補が毎回先に枠を試すため、下位ルールの
候補が届かない状態が続き得る。`ALL_MEMBERS_LIMITED`が再試行可のまま2か月で期限切れ削除され再候補になるため、
実質「上位ルール優先の無限リトライ」になる。

要件が明示的に選んだ優先順位設計であり変更しない。ホーム履歴に「上限超過で見送りN件」を出す設計（§9.1）で
利用者が状況を把握できることを維持すること。

### R1: 採用

**確認済み**。実サイトでは取消済み行が一覧に残り、同一`tilcod`の予約中行と取消済み行が併存し得る。
自動予約の除外判定は行の有無だけではなく状態を見る必要がある。

実装規則は次のとおりとする。

- 同一`tilcod`のうち、`ReservationState.CANCELLED`以外の行が1件以上あれば除外する
- 取消済み行しかなければ予約中の除外根拠にしない
- `IN_TRANSIT`・`READY`は有効な予約として除外する
- 同一`tilcod`に取消済み行と有効な予約行が併存するテストを必須にする

なお、現行`StatusRepositoryImpl`はRoom保存時に取消済み行を除外しているが、自動予約用の最新スナップショットは
サイト応答を直接扱うため、設計上の明文化は必要である。

### R2: 修正案を不採用

**確認済み**。`docs/spec.md`§3.11は、自動予約を「新着資料の取得と全置換が正常終了した直後」に実行し、
取得結果が前回と同じ場合でも**正常に再取得した場合**は再試行すると定めている。
12時間の鮮度抑止で取得を省略した場合は、新着更新が発生していない。

したがって、元レビューの「取得をスキップしてもキャッシュをevaluateする」案は次の理由で採用しない。

- 確定済みの実行契機を「画面を開いた時」へ実質的に拡張する
- 12時間以内に画面を開くたび、全メンバーのログインと再試行が起こり得る
- 「上限超過・POST前失敗は次回の新着更新で再試行する」という要件と一致しない

設計書には曖昧さを残さないため、次の3分岐を明記する。

- 取得成功・全置換成功: evaluateする
- 取得失敗: evaluateしない
- 鮮度抑止による取得スキップ: evaluateしない

既存の明示的な「更新」は鮮度に関係なく取得するため、利用者が早期再試行を望む場合の導線も既にある。

### R3: 問題提起を採用するが、安全性の説明を修正

**確認済み**。不完全な予約一覧に対象`tilcod`が無いことを「予約していない」という陰性証拠にはできない。
一方、元レビューの「不完全なメンバーを予約先候補から外せば家族内重複を許容しない側へ倒せる」という説明は
正しくない。不完全なメンバーAに実際は予約があり、完全なメンバーBへ続行すれば家族内重複は起こり得る。

確定要件が次順位への続行を明示しているのは、POST前と確定できる認証・通信失敗である。元設計はこれを
パース失敗にも広げ、取得できたメンバーで処理を続けるトレードオフとしている。不完全一覧を同じ部分失敗として
扱う場合も、家族内重複を防げると誤認せず、元設計と同じ残存リスクを明記する。

- 不完全一覧で見つかった非取消の陽性一致は、家族共通の除外根拠に使う
- 不完全一覧で見つからないことは、不在証明として記録しない
- 当該メンバーはその回の予約先候補から外す
- 他の取得成功メンバーで続行する場合、家族内重複の可能性が残ることを履歴・設計リスクへ明記する
- 全メンバーが取得失敗または不完全ならPOSTせず、再試行可能として終了する

家族内重複を一切許容しない方針へ変更するなら、1人でも陰性不完全があった候補を家族全体で停止する必要がある。
これは現在の部分失敗継続要件を変更するため、別途所有者判断なしには採用しない。

### R4: 指摘された停止点は明文化するが、提案されたカラムでは解決しない

**確認済み**。`PREPARED`から次順位メンバーへ進む状態遷移が曖昧なままでは、不要な取り逃しが生じ得る。
ただし、元レビューの`lastSettledMemberId`案は安全ではない。

例えばメンバーAの上限超過を確定後、メンバーBについて`PREPARED`を書き、BのPOST直後に停止した場合、
`lastSettledMemberId=A`と「Aより後に未試行メンバーがいる」という情報だけでは、Bが未送信かPOST後不明かを
区別できない。ここでBから再開すると、同一メンバーへの二重送信になり得る。

採用する状態遷移は次のとおり。

1. メンバーへのPOST直前に、`preparedMemberId`を含む`PREPARED`を永続化する
2. 明示的上限超過やPOST前失敗など、結果が確定したら、次メンバーへ移る前に`PREPARED`を
   再試行可能状態へ確定更新する
3. その後、次メンバーのPOST直前に、そのメンバーを対象とする新しい`PREPARED`を書く
4. 起動時に`PREPARED`が残っていれば、`preparedMemberId`のPOST成否は不明として資料全体を
   `UNKNOWN_AFTER_POST`へ倒し、同じ資料を誰にも自動再送しない

POST応答を受け取ってからRoomへ結果を確定するまでの停止窓はネットワークとDBを原子的にできない以上残る。
この窓による取り逃しは、二重予約防止を優先する既存設計どおり許容する。

### R5: 条件付きで採用

送信時に指定した受取館の記録は、自動予約だけでなく手動カート・即時予約にも関係するため、
自動予約の制御記録へ埋め込まず、共通のローカル記録として設計する。

- キーは`memberId + tilcod`
- `Success`が確定したときだけ保存・更新する
- `AlreadyReserved`と`Unknown`では今回の指定館が反映されたと断定できないため保存しない
- サイトが確定館を表示できる場合はサイト値を優先し、ローカル値は「送信時の指定館」と明示する
- アプリから受取館を変更する機能は追加しない

元レビューの掃除条件は不足している。不完全な一覧で対象が見つからないことを根拠に削除すると、
有効な記録を失う可能性がある。**完全と確認できた一覧に非取消の対象行が無い場合だけ削除**する。
取消済み行しかない場合は有効予約が無いため削除してよい。手動・自動双方の成功結果から同じ記録処理を
呼ぶが、通信結果を解決するResolver自体へRoom依存を直接持たせない。

### R6: 採用するが、分類定義を追加する

所有者との相談で、端末通知に成功・見送り・エラーの件数を含めてよいとされた変更は採用する。
書名、ルール名、メンバー名、個別のサイトメッセージは引き続き通知へ含めない。

実装前に少なくとも次を正本仕様で定義する。

- `Success`と`AlreadyReserved`を「成功」に合算するか
- 上限超過、設定不足、OFFルールを「見送り」のどこまでに含めるか
- 認証・通信・パース、サイト拒否、POST後不明を「エラー」へどう分類するか
- OFFルールだけの回は通知しないという既存条件と、見送り件数表示との関係

分類は表示専用とし、予約再送可否を決める制御状態とは分離する。

### R7・R8: 採用

予約サイトが画面遷移状態へ依存することは実測済みである。利用状況取得は最初から分離セッションを使い、
予約用セッションでは実サイト成立確認済みのリクエスト順・メソッド・フォーム構造を変えない。
元レビューの「1バイトも変えない」は文字どおりの同一バイト列ではなく、この遷移契約を維持する意味とする。

ただし、既存`fetchUserData()`をそのまま使うと本棚・読書履歴まで取得するため、通信削減の目的に反する。
同じログイン準備とパーサを再利用しつつ、貸出・予約一覧と完全性だけを返す分離読み取り経路を設ける。

`ReservationSubmissionResolver`抽出は単独コミットにし、ユニットテストとCI成功後、CIのAPKで
カート予約・即時予約の実機結果をHEAD SHAとともに記録してから自動予約へ接続する。

### R9: 目的は理解するが、初期実装では採用しない

**確認済み**。現行`SyncResult.Completed`が持つのは成功人数と失敗人数だけで、成功したメンバーID、
取得した予約一覧、一覧完全性を呼出し側へ返さない。またRoomの予約一覧は取消済み行を除外して保存し、
取得時点・完全性も保持していない。

この状態で、SCHEDULED直前のRoomを「完全な最新スナップショット」とみなすことはできない。
初期実装ではR7の分離読み取りを優先し、通信の重複を正しさと交換しない。

将来最適化する場合は、`syncAll`の集計値ではなく、同一実行で取得したメンバー別スナップショットと完全性を
内部境界から直接Coordinatorへ渡す。Roomを読み直して推測する方式は採らない。

一方、元レビューが指摘したWorkManagerの再試行問題は正しい。現行`SyncWorker`は部分失敗時に最大2回
`Result.retry()`を返すため、自動予約を同じ`doWork()`へ接続する際は次を保証する。

- 予約候補が`PREPARED`へ一度でも到達した実行は、Worker全体を自動再試行しない
- 新着取得前または候補準備前の失敗だけ、既存の再試行規則を適用できる
- Workerの最終判定は同期集計だけでなく、自動予約のPOST境界到達有無を入力に含める

### R10: 不採用

最新履歴を1行JSONへまとめる案はテーブル数を減らすが、次のコストがある。

- enumや表示モデル変更時にJSON互換性を別途維持する必要がある
- 項目単位の型制約と外部キー整合をRoomで検証できない
- JSON全体の解析失敗で直近履歴を丸ごと表示できなくなる
- 親行と子行の全置換はRoomトランザクションとCASCADEで十分単純に保てる

表示用の一致ルール・メンバー試行詳細だけをJSONスナップショットにする元設計を維持し、
実行概要と資料行は`auto_reservation_latest_run`・`auto_reservation_latest_items`の2テーブルで保持する。

初回ON時のプレビュー・独自上限、ローカル予約カート除外、下位ルールの飢餓対策は追加しない。
いずれも既に所有者がトレードオフを理解したうえで決定しており、元レビューに記載された不採用理由を
設計書へ残す。

### 元レビューに不足していた横断事項

設計書修正時は、上記採否に加えて次を反映する。

1. **処理開始時スナップショット**
   マスタースイッチと既定館だけでなく、ルール内容・ルール順・メンバー順も開始時に固定する。
   実行中の設定変更で候補順や割当先を変えない。
2. **受取館記録の安全な掃除**

3. **通知分類と制御分類の分離**

### R2: 撤回する

設計者の反論が正しい。`docs/spec.md`§3.11の実行契機は「新着資料の取得と全置換が正常終了した直後」であり、
鮮度抑止でスキップした場合は新着更新が発生していない。取得をスキップしてキャッシュだけ評価する案は、
確定要件の実行契機を「画面を開いた時」へ拡張するものであり、レビュー側の要件解釈が誤っていた。
「再試行可候補が処理されない」という懸念も、日次Workerが毎日必ず取得・評価する限り成立しない。撤回する。

**ただし、撤回の前提が設計に書かれていない。** 上記の「日次Workerが毎日必ず取得する」は、
鮮度抑止が`SCREEN_AUTO`にのみ適用される場合にしか成り立たない。現在12時間の抑止は
`NewArrivalsScreenController.shouldAutoRefresh`（画面側）にあるが、設計§2.1は
「画面表示時の自動更新、既存の更新操作、日次WorkerはすべてCoordinatorを呼ぶ」としており、
再レビューの3分岐（取得成功／取得失敗／鮮度抑止によるスキップ）はCoordinator側の分岐として書かれている。

抑止判定をCoordinatorへ集約したうえで全トリガーに適用すると、**利用者が日次Worker実行時刻の12時間以内に
新着画面を開いていた日は、その日の自動予約が丸ごと走らない。** 就寝中に人気新刊を確保するという本機能の
目的が、画面を開くという無関係な操作で失われる。

条件: 設計書へ**「12時間の鮮度抑止は`SCREEN_AUTO`にのみ適用し、`SCHEDULED`と`SCREEN_MANUAL`には適用しない」**を
明記すること。テストで`SCHEDULED`が鮮度に関わらず取得することを固定すること。

### R3: 指摘は受け入れる。結論は再考を求める

「不完全なメンバーを予約先から外せば家族内重複を許容しない側へ倒せる」という元レビューの説明は誤りである。
メンバーAの一覧が不完全でAが実際に予約を持っていても、Bへ続行すれば重複は起こる。指摘のとおりであり、
説明の訂正に異議はない。

**しかし、そこから導かれた「当該メンバーはその回の予約先候補から外す」という結論は、根拠を失っている。**

外す目的が家族内重複の防止でないなら、残る目的は「そのメンバー自身が既に予約している資料へ再送しない」ことだけである。
ところがその場合のサイト応答は**`AlreadyReserved`であり、既存実装が安全に解決できる分類**である
（`docs/spec.md`§3.10、重複時alert「予約済の書誌があります。」）。副作用は無く、制御記録も終端へ確定する。

一方、外した場合のコストは実質的である。

- 家族の一部の一覧が不完全なだけで、その回の予約先が減る
- 全メンバーが不完全なら1件も予約しない（再レビューの規則）
- 所有者が示した本機能の趣旨は「気付いていなくても取り急ぎ待ち順位を高くする」ことであり、
  取り逃しのコストは重複予約の1回のPOSTより大きい

したがって次を提案する。

- 不完全一覧のメンバーも**予約先候補として使う**
- 陽性一致（非取消行が見つかった）は従来どおり家族共通の除外根拠にする
- 陰性は不在証明として使わない（合意済み）
- 同一メンバーへの重複送信は`AlreadyReserved`として解決し、終端とする
- 「全メンバーが不完全ならPOSTしない」規則は不要になる

一覧が不完全なメンバーを外すべきなのは、**完全性が確認できないと成否照合ができない場合**である。
再レビューはここを区別していない。POST後の照合に使う一覧の完全性要件（`ReservationListSnapshot.complete`）は
既存の予約成立判定の話であり、**事前の除外判定の完全性とは別の要件**である。設計書では両者を別々に書くこと。

### R4: 撤回する

設計者の反論が正しい。`lastSettledMemberId`と「未試行メンバーが残っていれば倒さない」という組み合わせでは、
メンバーBについて`PREPARED`を書いた直後に停止した場合と、BのPOST後に停止した場合を区別できず、
Bへの二重送信を許す。レビュー側の提案は安全でなかった。撤回する。

再レビューの状態遷移（結果確定のたびに`PREPARED`を再試行可能状態へ確定更新し、次メンバーのPOST直前に
新しい`PREPARED`を書く）は、元レビューが問題視した停止窓（Aの上限超過確定後、Bの`PREPARED`書込み前の中断）を
カラム追加なしで解決している。設計として優れている。

**1点だけ確認したい。** 再レビューの手順4は「`PREPARED`が残っていれば`preparedMemberId`のPOST成否は不明として
資料全体を`UNKNOWN_AFTER_POST`へ倒す」としており、判定に`preparedMemberId`を使っていない。
この列は制御判定には不要で、履歴・診断用途にしか効かない。診断へ`memberId`を記録すること自体は
設計§11で許容されているため保持に異議はないが、**「制御判定には使わない列である」と設計書へ明記すること**。
将来の実装者が判定条件に使い始めると、撤回した提案と同じ不安全へ戻る。

### R5: 掃除条件は合意。`Unknown`不保存は差し戻す

掃除条件を「完全と確認できた一覧に非取消の対象行が無い場合だけ削除」とする修正は、元レビューより厳密であり合意する。
Resolverへ直接Room依存を持たせない点も合意する。

**`Unknown`では保存しない、という判断には反対する。**

この記録が表すのは**「アプリがこの受取館を指定して送信した」というアプリ側の事実**であって、サイトの予約状態ではない。
所有者がこの機能を求めた目的は「万が一想定外の館で予約送信されていても、実サイトで修正できるようにする」ことである。

`Unknown`を保存しないと、**目的に最も合致する状況で記録が欠ける**。

1. 確定POST後に通信断（`Unknown`）
2. 実際にはサイト側で予約が成立していた
3. 次回同期で予約一覧に現れる（割当前なので受取館は「未定」表示）
4. **どの館を指定して送ったのかを確認する手段が無い**

「成否不明を予約済みと誤読させる」という懸念は、記録の保存ではなく**表示**の問題である。
表示側で区別できることは元レビューが既に条件として示している。

提案:

- `Unknown`でも保存する。ただしレコードに「送信結果の分類」を持たせる
- 表示は、予約一覧に**実際に行が存在する場合にだけ**行う。`Unknown`の記録が単独で存在しても
  予約一覧に行が無ければ何も表示しない（誤読の余地が消える）
- 予約一覧に行があり、かつ記録が`Unknown`由来である場合も、表示文言は`Success`由来と同じ
  「送信時の指定館」でよい。行が存在する時点でサイト側に予約は存在しており、成否不明ではない
- `AlreadyReserved`で保存しない判断は合意する（今回の指定が反映されていないため）

### R6: 分類の具体案

再レビューが所有者判断へ差し戻した4点について、レビュー側の案を示す。所有者の裁定を仰ぐ。

| 通知上の分類 | 含める結果 |
|---|---|
| 成功 | `Success`、`AlreadyReserved` |
| 見送り | 全メンバー上限超過、設定不足（既定館未設定・館が選択肢に無い等）、個別ルールOFF |
| エラー | 認証・通信・パース・メンテナンス、サイト拒否(`REJECTED_BY_SITE`)、POST後不明 |

補足:

- 正常除外（予約中・貸出中・読書記録・制御記録による除外）は件数に含めない。§9.1で履歴の上書き対象外と
  されているものを通知へ出すと、毎日「見送りN件」が出続けて情報価値が失われる
- **POST後不明を「エラー」へ丸めることには留保がある。** 実際には成立している可能性があり、
  利用者にとっては「予約されたかもしれない」という固有の状態である。通知は3分類で構わないが、
  **ホームの詳細ダイアログでは独立した区分として表示する**こと
- OFFルールだけの回は通知しない（既存条件を維持）。この場合「見送り」件数は通知に現れないが、
  ホーム履歴には残る
- 分類は表示専用であり制御状態を丸めない、という再レビューの原則に合意する

### R7: 合意。ただし「新経路の新設」ではなく「既存経路の打ち切り」に

分離読取セッションを採る点、および「1バイトも変えない」を遷移契約の維持と読み替える点に合意する。

**ただし「同じログイン準備とパーサを再利用しつつ、貸出・予約一覧と完全性だけを返す分離読み取り経路を設ける」を、
新しい遷移列の設計として実装しないこと。** それではR7の安全性根拠（実績のある経路をそのまま使う）が失われる。

`LicsXpClient.fetchUserData`の実際の順序は**確認済み**で、次のとおりである。

```
（分離セッション確立）→ ログイン → usrlend → usrrsv → mybooklist →（必要なら usrread）
```

必要なのは`usrlend`と`usrrsv`までであり、**この2つは既存経路の先頭2ページである**。したがって
「新しい経路を作る」のではなく、**既存の遷移列を`usrrsv`の直後で打ち切る**形にすればよい。
`mybooklist`以降を実行しないだけで、それ以前のリクエスト順・メソッド・パラメータは1つも変わらない。

設計書には「既存`fetchUserData`の遷移列の前半（ログイン→`usrlend`→`usrrsv`）をそのまま用い、
`mybooklist`以降を実行しない」と書くこと。実装は共通化でも分岐でもよいが、**送信されるリクエスト列が
既存経路の接頭辞と一致することをMockWebServerで固定**すること。

### N1. 【新規】手動予約と自動予約の同時実行が設計に無い

**確認済み（記述漏れ）**。設計§8.2の`Mutex`は`NewArrivalUpdateCoordinator`の二重呼出しを防ぐだけで、
**手動予約（カート確定・即時予約）との競合を防がない。** 自動予約の実行中に利用者が予約カートを確定すると、
同一資料・同一メンバーへ2系統からPOSTが飛び得る。

既存の「サイト全体のレート制御mutex」（`docs/handoff.md`、確認GET→確定POSTの排他区間）は500ms間隔と
確認〜確定の割り込み防止のためのものであり、同一資料への二重予約を防ぐ機構ではない。

実害は限定的（サイト応答は`AlreadyReserved`になり既存実装が解決する）だが、設計に一言も無いのは危うい。
少なくとも次を設計書へ書くこと。

- 手動予約と自動予約が同時に走り得ること、およびその場合の結末（`AlreadyReserved`で解決）
- 自動予約の実行中に手動確定を禁止するか否か（禁止しないなら、その判断と理由）
- 自動予約が書き込み中であることをUIが知る手段があるか（新着画面の更新中表示だけでは足りない）

### N4. 【新規】実行中のメンバー構成変更

再レビューの横断事項1（ルール内容・ルール順・メンバー順を開始時に固定する）に合意する。**そのうえで、
メンバーの追加・削除が実行中に起きた場合が抜けている。**

- 開始時スナップショットに含まれるメンバーが、実行中に削除された場合の扱い
- 実行中に追加されたメンバーはその回の対象外とすること（スナップショット方針から自明だが明記する）

削除されたメンバーへPOSTするとログインが失敗し、POST前失敗として次順位へ進むだけなので実害は小さいが、
`FamilyRepository`の削除がRoomの認証情報を消すため、例外分類が`AUTH`になるか別の失敗になるかは
実装依存になる。開始時スナップショットのメンバーが実行時に存在しない場合は、**POSTを試みずスキップする**のが
安全である。
